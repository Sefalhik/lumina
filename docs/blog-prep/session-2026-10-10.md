# Session 2026-10-10 — Ça marchait, pour la mauvaise raison

## Contexte

Un samedi, avec une question de départ simple : le rapport de failles de l'issue GitHub ne dit rien
de circonstancié, alors qu'il reste une alerte « critical » sur le projet. *Une idée de ce qui ne va
pas ?*

Rien n'était en panne. Mais la journée a enchaîné quatre fois le même constat, sur quatre objets
différents : quelque chose fonctionnait, et pas pour la raison qu'on croyait. Un tableau de bord
vide par construction. Une tolérance devenue fausse sans que personne le dise. Un script qui
téléchargeait depuis une adresse abandonnée. Des tests verts parce qu'un autre contrôle refusait à
leur place.

---

## 1. Le rapport qui n'en était pas un

L'issue en question est le Dependency Dashboard de **Renovate**. Dependabot n'écrit dans aucune
issue : ses alertes vivent dans l'onglet Security.

La rubrique « Vulnerabilities » du tableau de bord annonçait « Renovate has not found any CVEs ».
Vrai, et attendu : elle lit OSV.dev pour les dépendances **directes** seulement, et les deux
alertes ouvertes sont transitives. LUMN-73 l'avait écrit trois jours plus tôt, dans
`renovate.json5` et dans la doc. Le lire dans la doc et le reconnaître devant l'écran, ce n'est pas
le même exercice.

Le rapport circonstancié existait, mais dans le dépôt : `accepted-advisories.json`, avec un motif
et une date de revue par avis. L'audit quotidien était vert parce que les deux avis y figuraient —
donc il n'affichait rien.

**Piste d'article** : un contrôle qui se tait quand tout est accepté ne se distingue pas, de loin,
d'un contrôle qui ne regarde pas.

---

## 2. Une tolérance périmée en deux jours

L'avis critique sur `shell-quote` était toléré avec ce motif : `concurrently` épingle la version
vulnérable « in its latest release too ». Vrai le 7 octobre. Le 8 à 12h53 UTC, `concurrently`
10.0.6 sortait avec `shell-quote` 1.12.0.

Aucun outil n'était fait pour le dire :

- **l'audit** connaît quatre issues, et « un correctif existe désormais pour un avis accepté » n'en
  fait pas partie. `npm audit` le sait pourtant : il répond `fixAvailable: true`. L'entrée serait
  restée verte jusqu'à sa date de revue, un mois plus tard ;
- **Renovate** voyait la 10.0.6, retenue par le délai de 3 jours puis par la fenêtre du lundi ;
- **la voie rapide sécurité** ne s'appliquait pas : l'alerte porte sur `shell-quote`, pas sur
  `concurrently`, et rien ne dit à Renovate que monter l'un corrige l'autre.

La décision a été d'attendre : forcer aurait contourné le délai, alors que l'analyse de risque du
motif tenait toujours. La cinquième issue de l'audit a été proposée, et laissée de côté ce jour-là.

**Piste d'article** : une date de revue protège contre l'oubli, pas contre un motif qui devient faux
entre-temps.

---

## 3. Le pré-vol

« Je ne vois rien de dangereux » dans les mises à jour proposées. Presque : le lot Composer montait
`larastan` en 3.13.0, qui exige PHPStan 2.3. Une mineure de l'analyseur statique, embarquée en
transitif dans une PR dite de routine, sur un projet au niveau 8 où les dépréciations sont des
erreurs.

Plutôt que d'attendre la CI, la mise à jour a été rejouée dans un worktree jetable : même
`composer update`, PHPStan sur les deux configurations, PHPUnit avec couverture. Vert : 561 tests,
99,75 % de lignes. La PR Renovate pouvait donc être traitée comme de la routine en connaissance de
cause.

Deux détails :

- le premier essai à blanc a échoué parce que le shell de la session résolvait `php` en 8.4, alors
  que le projet exige 8.5 : il a fallu appeler `php8.5` explicitement, jusque dans le hook de
  pré-commit ;
- le lockfile réellement mergé contenait **moins** que le pré-vol : Renovate n'a pas monté
  `laminas-diactoros` ni `laravel/prompts`. Sans conséquence, la CI de la PR ayant validé la
  combinaison réelle — mais un pré-vol teste une hypothèse, pas la PR.

**Piste d'article** : « mineure et patch » décrit la version demandée, pas ce qu'elle entraîne.

---

## 4. Ce qu'on a laissé attendre

Cocher toutes les cases du tableau de bord aurait donné moins bien que d'en cocher deux :

- la PR npm n'aurait porté que `vite` 8.3.3, dépassé le lendemain par 8.3.4, et pas encore
  `concurrently` 10.0.6 ;
- les actions GitHub étaient sous leur délai, et ce délai est la seule garde contre une release
  d'action compromise ;
- la lock file maintenance, passée avant les autres, aurait absorbé les mises à jour directes.

Avec le mode strict, chaque merge impose un rebase des PR restantes : l'ordre n'est pas un détail.

---

## 5. Vérifier à la main, et voir que le script ne le fait pas

FrankenPHP venait de passer en 1.13.0. Vérification demandée : est-ce que tout est correct ?

Version, capacité réseau, extensions, worker, réponses HTTP — et une comparaison de l'empreinte
SHA-256 du binaire avec celle que GitHub publie pour l'asset. Identiques.

C'est cette comparaison, faite à la main, qui a montré que `scripts/update-frankenphp.sh` ne la
faisait pas. Il installait ce qu'il recevait : aucune empreinte, aucun délai, un `curl` sans
`--fail` qui aurait enregistré une page d'erreur à la place du serveur. Signalé comme dette hors
périmètre. La réponse : *c'est une faiblesse de notre outillage, on gère ça.*

**Piste d'article** : le binaire téléchargé par un script maison est la dépendance que plus aucun
outil ne regarde.

---

## 6. Trois contrôles, et ce que chacun vaut (LUMN-74)

| Contrôle | Ce qu'il prouve | Ce qu'il ne prouve pas |
|---|---|---|
| Empreinte | le fichier est celui que GitHub détient | que la release est honnête : l'empreinte et le binaire ont la même origine |
| Délai | une release compromise a eu le temps d'être retirée | rien sur une compromission découverte plus tard |
| Origine | la réponse vient du dépôt attendu, sans intermédiaire | — |

L'empreinte est le contrôle le plus visible et le moins protecteur des trois. Elle attrape un
téléchargement tronqué. Contre une release malveillante, c'est le délai qui travaille — le même que
pour npm et pour les actions.

D'où la consigne : si la valeur de ce délai est centralisée quelque part, le script l'utilise. Elle
l'est, dans `.npmrc`, et `ReleaseAgeParityTest` la tient déjà égale à celle de Renovate. Le script
la lit. Une troisième copie aurait été un chiffre de plus à oublier.

Trois choix d'implémentation, laissés à confirmer en revue : une release trop jeune est « retenue »
avec un code de sortie 0, parce que rien n'est cassé ; `--min-release-age=0` permet d'installer une
release de sécurité une fois ses notes lues ; un argument inconnu est refusé au lieu d'être ignoré —
une faute de frappe sur l'option censée retenir une release l'aurait installée.

## 7. La redirection qui marchait

Le script interrogeait `dunglas/frankenphp`. Le projet a déménagé vers `php/frankenphp`, GitHub
redirige, `curl -L` suit : tout fonctionnait, et rien ne disait que le script dépendait d'une
redirection.

Renommer le dépôt dans le script corrige aujourd'hui. Cela ne dit rien du prochain déménagement.
L'appel à l'API se fait donc **sans** `-L` : un 301 arrête le script, avec la consigne de changer
le nom. Le téléchargement, lui, garde `-L` — GitHub sert chaque asset depuis un autre hôte — et
c'est pour cela que l'adresse est comparée avant, et l'empreinte après.

**Piste d'article** : suivre une redirection, c'est faire confiance à celui qui possédera l'ancien
nom demain.

---

## 8. Une doublure qui se comporte comme curl

Jusqu'ici, aucun script shell du dépôt n'était exécuté par la suite de tests : `check.sh` est lu,
pas lancé. Celui-ci est lancé pour de vrai, dans un dossier temporaire, avec un `PATH` qui ne
contient que ce que le test y a mis — les vrais outils nécessaires, et des doublures de `curl`,
`uname`, `date` et `sudo`.

La doublure de `curl` ne se contente pas de répondre. Elle ne suit une redirection que si on lui
passe `-L`, et n'échoue sur une erreur HTTP que si on lui passe `--fail`. Sans cela, aucun test
n'aurait pu distinguer `curl -L` de `curl` — or le script a besoin du premier pour télécharger, et
ne doit surtout pas l'avoir pour interroger.

## 9. Quatre mutations, et une cinquième mal faite

126 tests verts au premier lancement, 129 après trois cas ajoutés. Puis 96 mutations du script, une
ligne à la fois : **cinq survivantes.**

Quatre désignaient le même trou. Le contrôle du tag de version (`v1.13.0`) pouvait être supprimé
sans qu'un test rougisse. Les tests correspondants passaient pourtant : la fixture changeait le tag
et laissait l'adresse de téléchargement sur une autre version, si bien que le contrôle d'adresse
refusait le premier. Le bon refus, par le mauvais contrôle — et une assertion trop lâche pour faire
la différence. Fixture rendue cohérente, messages vérifiés un par un.

La cinquième était une mutation mal construite : `refuse … || true` ne change rien, puisque
`refuse` sort avant que le `||` soit évalué. Une mutation équivalente ne dit rien des tests ; elle
a été remplacée par une vraie.

Après correction : 133 tests, 97 mutations, zéro survivante.

**Piste d'article** : un test qui passe pour la mauvaise raison a exactement la même couleur que
les autres.

---

## 10. Ce que les doublures ne peuvent pas prouver

Les doublures simulent GitHub tel qu'on le suppose. Trois exécutions ont donc eu lieu contre le vrai :

- le binaire à jour est reconnu comme tel ;
- l'ancien nom de dépôt est refusé sur un vrai 301 ;
- une installation complète dans un bac à sable télécharge 175 Mo et produit un fichier dont
  l'empreinte est celle du binaire du projet.

Le cas « release retenue » n'a **pas** été confirmé en réel : l'essai a échoué pour une raison
étrangère au script, et n'a pas été refait. Il ne tient que par les tests.

## Pistes d'articles

- **Ça marchait, pour la mauvaise raison.** Un tableau de bord vide, une tolérance périmée, une
  redirection suivie, des tests verts : quatre fois le même défaut dans une journée.
- **Une date de revue ne voit pas un motif devenir faux.** L'avis accepté dont le correctif est
  sorti le lendemain.
- **« Mineure et patch » décrit la demande, pas ses conséquences.** La mineure de PHPStan cachée
  dans une PR de routine, et le pré-vol dans un worktree jetable.
- **Le binaire que plus aucun outil ne regarde.** Ce qu'installe un script maison, et pourquoi ni
  Renovate ni les alertes n'y peuvent rien.
- **Une empreinte ne prouve pas l'honnêteté.** Ce que couvre un SHA-256 publié par la même source
  que le fichier, et ce que couvre l'attente.
- **Suivre une redirection, c'est signer en blanc.** Le dépôt qui avait déménagé sans que rien ne
  casse.
- **Une doublure doit se tromper comme l'original.** Simuler `curl` assez fidèlement pour qu'un
  test distingue `-L` de son absence.
- **Le bon refus, par le mauvais contrôle.** Quatre mutations survivantes derrière des tests verts,
  et ce que vaut une assertion qui ne nomme pas le message attendu.
