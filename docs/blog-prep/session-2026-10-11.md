# Session 2026-10-11 — « Deployed », et rien n'avait changé

## Contexte

Dimanche, dans la foulée du premier déploiement lancé depuis GitHub (LUMN-50, fusionné le matin).
Deux chantiers : mettre à plat la livraison par versions, qui n'avait jamais été pensée, puis
LUMN-51 — construire chaque version à part, basculer d'un seul lien, pouvoir revenir en arrière.

Les deux sessions de la veille avaient chacune leur fil : « ça marchait, pour la mauvaise raison »,
puis « ça échouait, pour la mauvaise raison ». Celle-ci ferme le triangle : **ça réussissait, et il
ne s'était rien passé**. Un script qui termine par `Deployed`, un code de sortie à 0, une sonde qui
répond honnêtement « aucune page cassée » — et quatre cent cinquante requêtes plus tard, le site
servait toujours la version d'avant.

---

## 1. Un tag n'est pas un marque-page

LUMN-53 prévoyait de poser un tag à chaque déploiement. En le relisant, la question est venue
d'elle-même : un tag de quoi ? Le projet n'avait ni versions JIRA, ni notes de version, ni rien
qui dise « ceci est un livrable ».

Décisions prises, rangées dans un epic à part (LUMN-76) avec son schéma d'ordre d'exécution :

- **un tag git est une version livrable, et rien d'autre.** Pas de tag de déploiement, pas de tag
  technique ;
- **numéro par date**, `AAAA.MM.N`. Un site personnel n'a pas d'API publique dont une version
  majeure annoncerait la rupture ;
- **la version se coupe par une PR**, la « PR de version ». JIRA garde en permanence une version
  ouverte, « Prochaine version » ; la coupe la renomme, la ferme, et en rouvre une ;
- **GitHub écrit dans JIRA, jamais l'inverse** ;
- **la ligne publique de la note de version vit dans un champ du ticket**, écrite par celui qui
  connaît le changement, au moment où il le fait ;
- **une version corrective est une version comme les autres.**

Le jeton JIRA nécessaire à l'écriture des versions a eu droit à son propre ticket (LUMN-81) plutôt
qu'à une ligne dans un autre : c'est un secret de plus, avec sa portée et sa rotation.

**Piste d'article** : on met des tags partout parce que c'est gratuit. Le jour où l'on veut
publier des notes de version, il faut d'abord décider lesquels veulent dire quelque chose.

## 2. Un répertoire par version, un lien pour les servir

Le serveur était une copie de travail, modifiée sur place. Pendant quelques secondes, un
déploiement servait le nouveau code avec les anciens fichiers compilés, et il ne restait rien vers
quoi revenir.

```
<site>/
├── repo/                   nu : ce que le serveur sait de git
├── releases/<instant>-<commit>/
├── shared/                 .env, storage/, le verrou
└── current -> releases/…   la seule chose qu'une bascule change
```

Trois choix qui ne sont pas dans tous les tutoriels :

- **chaque version se construit avec son propre script.** `release.sh`, celui de la version en
  service, ne fait qu'extraire le commit ; il passe la main au `deploy.sh` *du commit extrait*.
  Changer la façon de déployer se déploie donc comme le reste ;
- **la porte décide et ne construit plus.** Elle prend le verrou, et le transmet ;
- **le verrou est un descripteur de fichier**, pas un fichier à supprimer. Il se libère quand le
  dernier processus du déploiement meurt, quelle que soit sa mort.

Et un quatrième, discuté : la clé du pipeline peut-elle demander un retour arrière ? Oui, mais
borné — défaire **le** dernier déploiement, **une** fois, pendant **une demi-heure**. Au-delà,
c'est exactement le « redéployer un vieux commit » que la porte refuse, et c'est refusé pareil.

## 3. La doctrine de test, appliquée à du bash

Deux fois dans la journée, la même question : « on couvre les chemins heureux et les erreurs
probables — et les autres ? ». Le disque plein au milieu d'une étape et le dépôt git corrompu ont
été déclarés indispensables. Ils l'étaient.

Ce que la chasse aux cas improbables a trouvé, dans du code dont tous les tests passaient :

- **une date lue en octal.** `((now - $when > 1800))` avec un `$when` commençant par zéro : bash
  lit de l'octal, échoue sur un `8`, et une erreur arithmétique dans une condition vaut « faux ».
  « Pas trop tard », donc. Une garde qui s'ouvre quand elle ne sait pas compter ;
- **une comparaison ratée lue comme « pas plus ancien ».** `git merge-base --is-ancestor` répond
  0, 1, ou autre chose quand il n'a pas pu répondre. Le `if !` rangeait « autre chose » avec 1 ;
- **une interruption juste après la bascule aurait supprimé la version en service.** Le script se
  fiait à un drapeau posé une ligne trop tard. Il demande maintenant au lien ;
- **une sonde de verrou qui répondait « tenu » à tout.** `flock fichier true` échoue aussi quand
  `true` n'est pas sur le `PATH` du test. « Je n'ai pas pu lancer la commande » et « je n'ai pas
  pu verrouiller » avaient le même code de sortie ;
- **l'injection de panne qui tombait sur le faux outil.** Le premier `mkdir` à échouer était celui
  de la doublure elle-même. Un test de garde compte désormais les appels de chaque écrivain.

Pour le disque plein : chaque écriture que les scripts font eux-mêmes échoue à son tour, et deux
passent par `/dev/full`. Pour le dépôt abîmé : de vrais objets retirés d'un vrai dépôt.

Et une réponse honnête à une question honnête — « le commit où `scripts/deploy.sh` serait un
dossier, ça vaut le coup ? ». Improbable, oui. Mais la vérification coûte une ligne (`100644 blob`
dans la sortie de `ls-tree`), et le jour où ça arrive, la clé ne répond plus à rien.

**Piste d'article** : en bash, l'erreur et le « non » ont souvent le même visage. Presque tous les
défauts trouvés ce jour-là sont des « je n'ai pas pu savoir » rangés du côté qui arrange.

## 4. La première bascule

Préprod migrée vers la nouvelle structure, à côté de l'ancienne, intacte. Premier déploiement
entre deux versions. `Deployed d54ea16…`. La sonde, qui interroge la page une fois par seconde et
demande chaque fichier compilé qu'elle nomme : aucune page cassée.

Sauf que l'en-tête `X-Release` disait toujours `cecb136`. Dix minutes plus tard aussi.

Une page de diagnostic déposée à la main a donné l'explication en cinq lignes. Apache suivait bien
le lien. PHP aussi, pour un script neuf. Mais OPcache retrouve `index.php` par le chemin qu'on lui
tend — `…/current/public/index.php`, qui ne change jamais — puis vérifie la date du fichier qu'il
a compilé la première fois, dans l'ancienne version. Ce fichier n'a pas bougé. Avec
`opcache.revalidate_path` à 0, la valeur par défaut, il ne regarde jamais où mène le lien.

Ce n'est pas un délai. Sans autre événement, l'ancienne version répond jusqu'au redémarrage de PHP.

Trois sorties possibles :

- **A. `revalidate_path=1` dans le panneau de l'hébergeur.** Un réglage hors du dépôt, et jusqu'à
  `realpath_cache_ttl` — 120 secondes ici — de retard : plus que la minute accordée au retour
  arrière ;
- **B. une adresse de remise à zéro appelée par le pipeline.** Une entrée de plus à protéger, un
  secret de plus ;
- **C. le contrôleur frontal pose la question.** Les premières lignes de `public/index.php`
  demandent quelle version le lien désigne — un `readlink` par requête. Si ce n'est pas la sienne,
  il fait oublier à PHP ce qu'il sait et passe la requête au contrôleur frontal de la bonne.

C, sans hésiter. La correction voyage avec le code, se teste, et vaut pour le retour arrière comme
pour l'avancée.

Le test le plus utile de la journée est né là : exécuter le **vrai** `public/index.php` dans un
site à deux versions. Il a attrapé, avant tout serveur, une classe déclarée deux fois au moment du
passage de relais.

Au passage, la même page a corrigé trois documents : PHP ne tourne pas en FPM chez alwaysdata,
mais en `cgi-fcgi`.

**Piste d'article** : le déploiement par lien symbolique est partout dans les tutoriels. La ligne
« et pensez à OPcache » y est beaucoup moins.

**Piste d'article** : une sonde qui répond « rien de cassé » a raison aussi quand rien n'a changé.
`watch-switch.sh` prend maintenant la version attendue en argument, et échoue si elle n'a jamais
répondu.

## 5. Un échec doit se raconter tout seul

Troisième défi de la journée : « comment se comportent les scripts en cas d'erreur, côté
reporting ? ». Un déploiement automatique n'a personne devant l'écran.

Les tests écrits pour y répondre ont trouvé deux mensonges :

- **un script interrompu annonçait « exit status 0 ».** Sans `trap` sur le signal, bash sort avec
  le statut de la commande qu'il attendait. Chaque signal devient maintenant le code qu'un shell
  lui donne, et passe par le compte rendu ;
- **un retour arrière pouvait annoncer un échec après avoir basculé.** Le compte rendu final
  demande désormais au lien ce qui est vrai, au lieu de déduire.

Un échec se termine par trois phrases : ce que le script faisait, ce que le site sert, ce qu'est
devenu le répertoire en construction. Le serveur garde une ligne par événement, et — ajout « vite
fait, mais bien fait » — **tout ce que chaque déploiement a dit**, dans un fichier par version.
Deux `tee`, un par flux, qui ignorent le signal qu'un terminal envoie en raccrochant : les derniers
mots d'un script qu'on interrompt sont justement ceux qu'il faut garder.

Limite observée sur le serveur, écrite dans la doc plutôt que cachée : deux tubes, donc pas d'ordre
garanti entre eux. Les deux dernières lignes de `composer install` sont arrivées sous le titre de
`npm ci`.

## 6. Le prix d'une mutation

La passe mécanique de la veille — supprimer chaque ligne tour à tour, relancer la suite — a servi
toute la journée, et sa facture aussi : sur quatre scripts et plus de quatre cents suppressions,
relancer toute la suite à chaque fois ne tient pas dans le rythme d'une retouche. En attendant
mieux, je n'ai rejoué à la main que ce qui avait changé.

Deux tickets d'outillage, séparés parce que l'intention est la même et la technique non : ne
rejouer que les tests concernés et paralléliser (LUMN-82) ; un vrai outil de mutation pour le PHP
(LUMN-83).

Un détail trouvé en chemin : la copie de sauvegarde que l'outil pose à côté du fichier muté a fait
échouer un test qui lisait tout le répertoire des workflows. Un outil de test qui casse les tests
des autres en travaillant — LUMN-82 déplace la copie.

## 7. Mesurer, pour de vrai

Deux mesures de neuf minutes sont parties dans le vide : la sonde tournait, la commande n'avait
pas été lancée, et deux commandes qui se ressemblaient trop ont fait croire à un mauvais commit.
Le protocole a été retourné — « prêt », la sonde démarre, la commande part — et tout a tenu en
vingt minutes.

Entre deux versions dont la feuille de style diffère, pour qu'une page servie avec les mauvais
fichiers se voie :

| | |
|---|---|
| Un déploiement | 50 s |
| Prise d'effet d'une bascule | à la requête suivante, sans redémarrer PHP |
| Un retour arrière | 1,4 s sur le serveur |
| Pages cassées | aucune, sur 750 requêtes à cheval sur un aller-retour |
| `.env`, `storage` | mêmes inodes avant et après |
| Second déploiement pendant le premier | refusé, statut 75 |
| Déploiement tué par `SIGKILL` en plein `composer install` | verrou libre en un dixième de seconde, site intact, répertoire orphelin retiré par le déploiement suivant |

Le dernier cas est le seul qu'aucun `trap` ne peut rattraper. Il a donc été joué pour de bon, sur
la préprod : un déploiement lancé dans sa propre session, un second demandé trois secondes après,
puis `kill -KILL` sur tout le groupe.

Une mesure ne pouvait se faire qu'après la fusion : le retour arrière demandé depuis GitHub.
L'environnement `preprod` n'accepte que `main`, et `main` ne connaissait pas encore cette demande.
Clé du pipeline tournée vers la nouvelle porte, huit sondes vertes, fusion — puis trois runs à la
suite : `deploy` (66 s), `rollback` (4 s), `deploy` (63 s). Cinq cents requêtes à cheval sur les
trois, aucune page cassée, test de fumée 19 / 19 après chacun.

Détail lu dans les horodatages : la nouvelle version répond huit secondes avant que le script ne
dise `Deployed`. Ce qui suit la bascule, c'est la suppression de la plus ancienne version.

## Pistes d'articles

- **« Deployed », et rien n'avait changé.** OPcache et les déploiements par lien symbolique : le
  diagnostic, les trois sorties, pourquoi la correction a sa place dans l'application.
- **L'erreur et le « non » ont le même visage.** Cinq gardes bash qui s'ouvraient quand elles ne
  savaient pas répondre.
- **Une sonde qui a raison pour rien.** « Aucune page cassée » est vrai aussi quand rien n'a été
  déployé. Mesurer l'effet attendu, pas seulement l'absence de dégât.
- **Un tag n'est pas un marque-page.** Décider ce qu'est une version avant d'en numéroter une.
- **Tuer un déploiement pour de vrai.** Ce que les tests simulent, et le seul cas qu'il a fallu
  jouer sur le serveur.
- **Le script qui raconte son échec.** Signaux, codes de sortie, et les derniers mots à garder
  quand la connexion tombe.
