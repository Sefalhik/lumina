## Partie 1 — Le crash `Class "Phar" not found` dans les workers PHPStan

### Le symptôme

```
Class "Phar" not found
```

Erreur dans les workers ReactPHP que PHPStan spawn pour l'analyse parallèle. La classe `Phar` est
une extension PHP intégrée — si elle n'est pas trouvée, c'est que le worker ne charge pas les
mêmes extensions que le processus principal.

### La cause : `PHP_INI_SCAN_DIR` non hérité

Sur ce système, les extensions PHP sont réparties en deux endroits :
- `/etc/php/8.5/cli/php.ini` — fichier principal (pointe vers la conf.d)
- `/etc/php/8.5/cli/conf.d/` — répertoire avec un `.ini` par extension (`20-phar.ini`, etc.)

PHPStan lance ses workers avec `-c /etc/php/8.5/cli/php.ini`. Mais les workers sont des processus
enfants lancés par `proc_open`, et dans ce contexte, `PHP_INI_SCAN_DIR` n'est pas hérité
automatiquement. Sans cette variable, PHP ne sait pas où chercher les ini supplémentaires, et
`phar.so` n'est jamais chargé.

### La solution

Exporter `PHP_INI_SCAN_DIR` dans la commande, ce qui force tous les processus enfants à le
recevoir par héritage d'environnement :

```json
"analyse": [
    "PHP_INI_SCAN_DIR=/etc/php/8.5/cli/conf.d ./vendor/bin/phpstan analyse",
    "PHP_INI_SCAN_DIR=/etc/php/8.5/cli/conf.d ./vendor/bin/phpstan analyse -c phpstan-tests.neon"
]
```

Wiring dans `composer.json` — pas dans un script shell ou un `.env` — pour que la commande soit
auto-documentée et portable pour tous les développeurs.

**Ce qu'on apprend** : les workers PHPStan (et plus généralement tout sous-processus `proc_open`)
ne voient pas l'environnement shell de l'appelant. Si une extension PHP manque dans un worker
mais pas dans le CLI normal, la première piste est toujours `PHP_INI_SCAN_DIR`.

## Partie 2 — 73 erreurs PHPStan vers zéro : tour des corrections

### Contexte initial

Avant cette session, `app/Http/Controllers/` et `app/Models/` étaient exclus de l'analyse via
`excludePaths` dans `phpstan.neon`. Pragmatisme de départ : corriger les erreurs ailleurs d'abord.
Quand on les réintègre, 8 erreurs supplémentaires apparaissent.

### Pattern récurrent : `$request->user()` retourne `Authenticatable|null`

PHPStan a raison : `$request->user()` est typé `Authenticatable|null` dans Laravel. Mais dans
les méthodes des contrôleurs auth, le middleware `auth` garantit qu'un utilisateur existe et que
c'est une instance `App\Models\User`.

**Solution uniforme** dans chaque méthode concernée :

```php
$user = $request->user();
assert($user instanceof User); // guaranteed by auth middleware
```

`assert()` est du PHP natif. PHPStan comprend que le type est `User` après cette ligne. Aucune
annotation, aucun `@phpstan-ignore`, aucune suppression — le type est réellement plus précis ici
et l'assertion documente pourquoi.

À noter : dans `verifyChallenge()`, la propriété `$user->two_factor_secret` est `string|null` —
parce qu'un utilisateur authentifié n'a pas forcément finalisé son enrôlement 2FA. Même si le
middleware `EnsureTwoFactorVerified` le garantit en pratique, PHPStan ne peut pas l'inférer.
La bonne solution n'est pas une annotation : c'est un guard explicite qui redirige vers le setup
si le secret est null. Comportement défensif correct + type narrowing.

### Le problème `unflattenJson` et le reference aliasing

Dans `AnthropicTranslator`, l'implémentation originale de `unflattenJson` utilisait des
références PHP pour construire un tableau imbriqué :

```php
$ref = &$result;
foreach (explode('.', $key) as $segment) {
    $ref = &$ref[$segment];
}
$ref = $value;
```

PHPStan perd le fil des types dès qu'une référence est créée. La solution : réécrire sans
références, avec deux helpers récursifs purs :

```php
private function expandKey(array $keys, string $value): array
{
    $head = array_shift($keys);
    return $keys === [] ? [$head => $value] : [$head => $this->expandKey($keys, $value)];
}

private function mergeDeep(array $base, array $overlay): array
{
    foreach ($overlay as $k => $v) {
        if (is_array($v) && isset($base[$k]) && is_array($base[$k])) {
            $base[$k] = $this->mergeDeep($base[$k], $v);
        } else {
            $base[$k] = $v;
        }
    }
    return $base;
}
```

Le code est plus lisible, entièrement typable, et PHPStan le comprend sans annotation.

**Ce qu'on apprend** : les références PHP (`&$var`) et PHPStan ne font pas bon ménage. Quand
PHPStan se plaint d'une variable "dont le type ne peut pas être déterminé", la première question
est : y a-t-il une référence dans le voisinage ?

### `Log::spy()` vs `Log::listen()` pour les tests

Dans `GeoServiceTest`, les tests vérifient que le service émet des logs d'avertissement sur erreur
API. L'approche initiale utilisait la syntaxe Mockery spy :

```php
Log::spy();
// ...
Log::shouldHaveReceived('warning')->with('...')->once();
```

PHPStan ne connaît pas `shouldHaveReceived` sur la façade `Log` — c'est une méthode magique
Mockery. Et `Log::fake()` n'existe pas dans cette version de Laravel (pas de `LogFake`).

**Solution** : `Log::listen()`, qui est déclaré dans le mixin Larastan de `Illuminate\Log\Logger`.
On capture les événements dans un tableau, puis on filtre avec `array_filter` :

```php
$captured = [];
Log::listen(function (MessageLogged $event) use (&$captured): void {
    $captured[] = $event;
});
Http::fake(['*' => Http::response(null, 503)]);
$this->service->locate(self::PUBLIC_IP);
$match = array_filter($captured, fn ($e) =>
    $e->level === 'warning'
    && $e->message === 'Geo API returned a non-2xx response'
);
$this->assertNotEmpty($match);
```

Plus verbeux, mais entièrement typé et sans dépendance sur les méthodes magiques de Mockery.

### Stub PHPStan pour `artisan()`

`$this->artisan('command')` dans les tests est annotée `PendingCommand|int` dans le framework,
mais l'implémentation retourne toujours `PendingCommand` — l'entier (`int`) n'apparaît que dans
le cas où on bypasse le wrapper, ce qui ne se produit jamais dans les tests PHPUnit.

Solution : un stub PHPStan dans `phpstan-stubs.php` qui surcharge la déclaration :

```php
namespace Illuminate\Foundation\Testing\Concerns;

trait InteractsWithConsole
{
    public function artisan(string $command, array $parameters = []): PendingCommand {}
}
```

PHPStan utilise cette déclaration en priorité sur l'annotation du framework. Zéro `@phpstan-ignore`,
zéro cast forcé.

## Partie 3 — Architecture PHPStan : deux configs, deux niveaux

### La question initiale

Deux angles aveuglants du setup de départ :
1. `app/Http/Controllers/` et `app/Models/` exclus → des bugs réels dans les contrôleurs auraient
   pu passer inaperçus
2. `tests/` analysé au même niveau que le code applicatif (niveau 8) → contrainte excessive pour
   des classes de test qui utilisent des APIs Mockery, des helpers PHPUnit, etc.

### La décision : deux fichiers de config

```
phpstan.neon          → app/  (excl. app/Providers/)  niveau 8
phpstan-tests.neon    → tests/                         niveau 5
```

Le niveau 5 pour les tests n'est pas du relâchement gratuit : il retire les erreurs liées aux
types génériques sur les collections, les méthodes magiques de test-helpers, etc., tout en
conservant les vérifications structurelles importantes (accès à des propriétés inexistantes,
appels de méthodes sur null).

**Ce qu'on apprend** : analyser les tests au même niveau que le code applicatif est
contre-productif. Le code applicatif doit être maximaliste pour attraper des bugs. Les tests
doivent être analysés pour prévenir des erreurs de structure, mais pas pour satisfaire des
contraintes génériques qui ralentissent l'écriture de tests clairs.

## Sujets d'articles potentiels

### Articles techniques

1. **"PHPStan niveau 8 dans un projet Laravel : le guide des 73 erreurs"**
   Inventaire des catégories d'erreurs les plus fréquentes dans un projet Laravel réel au niveau 8 :
   nullable `$request->user()`, types de collection non paramétrés, retours `mixed` de helpers,
   références PHP qui cassent l'inférence de types. Solutions systématiques sans `@phpstan-ignore`.

2. **"assert() comme outil de type narrowing — pas juste pour le debug"**
   `assert()` n'est pas réservé au debug. PHPStan le comprend comme un rétrécissement de type.
   Dans les contrôleurs Laravel, derrière un middleware `auth`, `assert($user instanceof User)`
   est à la fois une documentation du contrat et un guard runtime. Comparaison avec les
   alternatives (`throw`, `@var`, `@phpstan-ignore`).

3. **"PHPStan workers et PHP_INI_SCAN_DIR : quand les extensions manquent dans les sous-processus"**
   Anatomie du problème : un processus PHP principal qui charge ses extensions via conf.d, et des
   workers `proc_open` qui n'héritent pas cette variable. Diagnostic pas à pas. Fix minimal.
   Applicable à tout outil qui spawn des workers (PHPStan, Psalm, Parallel).

4. **"Log::spy() vs Log::listen() dans Laravel : ce que PHPStan accepte et ce qu'il refuse"**
   `Log::spy()` + `shouldHaveReceived()` est la syntaxe Mockery — non typable, non déclarée dans
   les mixins Larastan. `Log::listen()` est dans le mixin, entièrement typable. Comparaison des
   deux approches en termes de lisibilité, maintenabilité et compatibilité statique.

5. **"Stubs PHPStan : corriger les annotations du framework sans toucher au vendor"**
   Cas d'usage : `artisan()` dans les tests, annoté `PendingCommand|int` par le framework mais
   retournant toujours `PendingCommand`. Comment écrire un stub minimal dans `phpstan-stubs.php`,
   comment le déclarer dans `phpstan.neon`, et pourquoi c'est préférable à un `@phpstan-ignore`.

6. **"Deux configs PHPStan dans un même projet : app/ au niveau 8, tests/ au niveau 5"**
   Argumentaire pour une asymétrie de niveau entre le code applicatif et les tests. Ce que le
   niveau 5 garde, ce qu'il retire. Comment chaîner deux configs dans `composer.json` sans
   complexifier le CI.
