## Partie 1 — Aligner PHP CLI sur FrankenPHP

La session précédente avait mis en évidence un mismatch : FrankenPHP embarque PHP 8.5.5 dans son
runtime, mais le binaire CLI système était en 8.4. Le Launchpad d'Ondřej Surý était en panne ce
jour-là. Il était temps de terminer le travail.

### Installation de PHP 8.5 CLI

`php8.5-cli` et toutes ses extensions utiles au projet (`php8.5-pgsql`, `php8.5-redis`,
`php8.5-xml`, `php8.5-mbstring`, `php8.5-curl`, `php8.5-zip`, etc.) s'installent depuis le PPA.
L'alignement se fait avec `update-alternatives` pour pointer `php` et `php8.5` sur le bon binaire.

Deux nouvelles extensions apparaissent dans PHP 8.5 : `lexbor` (parseur HTML5 natif) et `uri`
(manipulation d'URIs conformes RFC 3986). Aucune utilité immédiate pour le projet, mais notables
pour l'avenir si on manipule du HTML ou des URLs complexes côté serveur.

### Configuration dev PHP

PHP 8.5 installé "nu", sans ini de développement. Un fichier drop-in `/etc/php/8.5/cli/conf.d/99-dev.ini`
corrige ça : `E_ALL`, `display_errors = On`, `zend.assertions = 1`, `opcache.revalidate_freq = 0`,
`memory_limit = 512M`, `date.timezone = Europe/Paris`.

FrankenPHP a sa propre couche PHP. Il charge les extensions depuis son répertoire interne —
impossible de lui pointer directement `conf.d` du CLI (ça génère des warnings sur les `.ini` qui
tentent de charger des `.so` introuvables). La solution : un répertoire dédié `/etc/php/8.5/frankenphp/`
avec uniquement les paramètres non liés aux extensions, et `PHP_INI_SCAN_DIR` dans `.env`.

La ligne dans `.env` : `PHP_INI_SCAN_DIR=/etc/php/8.5/frankenphp`. FrankenPHP la lit au démarrage
d'Octane. Le CLI lit son propre `conf.d` comme d'habitude. Les deux environnements sont correctement
configurés sans interférence.

## Partie 2 — Epic A : Authentification + 2FA

### La question architecturale : logique dans les contrôleurs ou dans des services ?

Avant d'écrire une seule ligne de code fonctionnel, une décision structurante : est-ce qu'on met
la logique dans les contrôleurs ou dans des services ?

La réponse est évidente en théorie. En pratique, sur un projet personnel, la tentation est forte
de faire des contrôleurs "gros" pour aller vite. Le problème se pose toujours au même moment :
quand on essaie d'écrire les tests unitaires. Un contrôleur qui instancie des modèles, vérifie des
rôles, génère des secrets TOTP et construit des URLs — c'est impossible à tester sans bootstrapper
tout le framework. Un service qui fait la même chose — c'est cinq assertions en 50 ms.

Décision prise dès le départ : deux services dans `app/Services/Auth/`.

**`LoginService`** ne fait qu'une chose : résoudre l'URL de redirection post-login en fonction du
rôle. C'est minuscule — mais c'est testable, nommé, et extensible sans toucher au contrôleur.

**`TwoFactorService`** encapsule tout ce qui touche à Google2FA : génération du secret Base32,
construction de l'URL `otpauth://` et rendu SVG du QR code, vérification d'un code TOTP avec
fenêtre de dérive d'horloge, et persistance du secret confirmé en base (chiffré par le cast
Eloquent `encrypted`).

La validation est isolée dans des `FormRequest` : `LoginRequest` (email + password) et
`TwoFactorCodeRequest` (6 chiffres exacts). Les contrôleurs ne savent pas comment valider — ils
délèguent.

### Le flow 2FA en trois états

L'admin qui tente d'accéder à `/fr/admin/` passe par trois middlewares dans l'ordre : `auth`,
`role:admin`, `two_factor_verified`.

`EnsureTwoFactorVerified` implémente une machine à trois états :

1. **Pas de `two_factor_confirmed_at`** → l'admin n'est pas encore enrôlé → setup
2. **Enrôlé mais pas de flag en session** → il faut vérifier l'identité cette session → challenge
3. **Flag présent** → passage

L'état 2 contient un détail important : avant de rediriger vers le challenge, le middleware stocke
l'URL courante dans `url.intended`. Ainsi, après un challenge réussi, `redirect()->intended()`
renvoie l'admin là où il voulait aller, pas systématiquement sur `/fr/admin/`. Ce comportement est
cohérent avec ce que fait le middleware `auth` lui-même pour les utilisateurs non connectés.

### Les deux clés de session

Le flow 2FA utilise deux clés de session bien distinctes :

- `auth.two_factor_setup_secret` : le secret temporaire généré lors du setup, conservé en session
  jusqu'à ce que l'utilisateur confirme avec un premier code valide. Cette clé est supprimée après
  confirmation. Elle ne va jamais en base à ce stade.

- `auth.two_factor_verified` : un boolean positionné à `true` après un challenge réussi. Il
  persiste pour toute la durée de la session. Si l'admin se déconnecte, la session est invalidée
  par `LogoutController` — ce flag disparaît avec elle.

La séparation est intentionnelle : le secret temporaire est une donnée sensible liée à une opération
en cours ; le flag de vérification est un état de session sans valeur en dehors de son contexte.

### Pourquoi trois étapes dans `LogoutController::destroy()`

```php
Auth::logout();
$request->session()->invalidate();
$request->session()->regenerateToken();
```

Ces trois lignes semblent redondantes. Elles ne le sont pas.

`Auth::logout()` retire les credentials du guard — l'utilisateur est déconnecté du point de vue de
Laravel. Mais la session existe encore avec toutes ses données.

`session()->invalidate()` détruit les données de session et génère un nouvel ID de session. Sans ça,
quelqu'un qui intercepte le cookie de session avant le logout pourrait encore lire les données de
session après.

`session()->regenerateToken()` génère un nouveau token CSRF. Sans ça, le prochain formulaire
(typiquement la page de login) n'aurait plus de token valide, et le premier POST échouerait avec
une 419.

C'est une séquence complète de "nettoyage post-déconnexion" — chaque étape est nécessaire.

### L'internationalisation des vues auth

Première erreur corrigée en cours de session : les vues auth avaient leurs chaînes hardcodées en
anglais dans `lang/fr/auth.php`. C'est exactement l'inverse de ce que la convention demande.
`lang/fr/` contient les valeurs **françaises** — les autres langues sont générées à partir d'elles.

Deuxième erreur : les valeurs de traduction commençaient par `//` (ex: `'// Secure Access Terminal'`)
alors que le `<span>//</span>` est déjà dans le HTML. Double affichage garanti. Fix : retirer le
préfixe des valeurs.

Troisième problème, de fond celui-là : les routes auth étaient hors du préfixe `/{lang}/`. Le
middleware `SetLocale` ne s'y appliquait jamais. Résultat : peu importe la langue de l'URL,
`app()->getLocale()` retournait `config('app.locale')` sur ces pages.

La solution naturelle : intégrer toutes les routes auth dans le groupe `/{lang}/`. Conséquence
directe : tous les `route()` sans paramètre `lang` dans les contrôleurs, le middleware 2FA et les
vues Blade doivent être mis à jour. Une vingtaine de points de contact. C'est mécanique mais
non-trivial à ne pas oublier.

Un point délicat : `bootstrap/app.php` configure la redirection du middleware `auth` avec
`redirectGuestsTo`. Il fallait aussi en tenir compte pour que les utilisateurs non connectés
soient redirigés vers `/{lang}/login` et non `/login`. Comme le middleware `locale` s'exécute
avant `auth` dans le groupe de routes, `app()->getLocale()` est déjà positionné au moment où la
redirection se calcule.

### Les labels de formulaire et la clarté UX

Un retour utilisateur instructif : le label "Access Code" sur le champ password de la page login
est ambigu. Quelques écrans plus loin, l'app demande un "code à 6 chiffres" pour le 2FA. Les deux
sont des "codes" — mais ils sont fondamentalement différents.

Le fix est simple : appeler les choses par leur nom. "Mot de passe" pour le password, "Code à
usage unique" pour le TOTP. La terminologie cyberpunk est un choix stylistique — pas une raison de
sacrifier la clarté.

### Logging et documentation du code

Les six fichiers de l'Epic A ont reçu des logs structurés et des docblocks en fin de session.

Sur les logs : la convention établie dans `docs/logging-conventions.md` (messages statiques,
contexte `service`/`method`/`step`, exceptions comme objet `Throwable` complet) s'applique ici
comme partout. Les tentatives de code TOTP invalides logguent en `warning` — comportement attendu,
géré gracieusement. La confirmation du 2FA et les connexions réussies loguent en `info` — événements
métier normaux.

Sur les docblocks : le principe reste "ne commenter que ce qui ne se lit pas dans le code". Les
trois étapes du logout en sont le meilleur exemple — elles surprennent à la première lecture, leur
raison d'être mérite une ligne. La fenêtre de dérive d'horloge de Google2FA (±1 intervalle de 30s
par défaut) aussi. Le cast `encrypted` sur `two_factor_secret` qui chiffre transparentement la
valeur avant insertion en base — idem.

## Ce qu'on retient

**Sur l'architecture service vs contrôleur.** La question n'est pas "est-ce que le contrôleur est
trop gros ?" mais "est-ce que je peux tester cette logique sans démarrer un serveur HTTP ?". Si la
réponse est non, le code est au mauvais endroit. Les services `LoginService` et `TwoFactorService`
pèsent chacun une quarantaine de lignes — mais ils ont des tests unitaires rapides et complets.

**Sur la machine à états du 2FA.** Raisonner en états explicites plutôt qu'en conditions imbriquées
évite les cas limites. Trois états, trois chemins, zéro condition sur plusieurs niveaux. L'état
"setup" et l'état "challenge" ont des sémantiques très différentes : l'un est un enrôlement
permanent, l'autre est une vérification par session. Les traiter avec le même code aurait été une
fausse économie.

**Sur les routes localisées pour l'auth.** C'est tentant de laisser `/login` hors du préfixe
linguistique — c'est "plus simple". Mais ça crée une incohérence : l'utilisateur voit `/fr/home`
dans la barre d'adresse, puis `/login` au moment de s'authentifier. La cohérence vaut le coût des
mises à jour de route.

**Sur les clés de session nommées explicitement.** `auth.two_factor_setup_secret` et
`auth.two_factor_verified` sont des noms verbeux. Intentionnellement. Une clé de session nommée
`s` ou `tfv` est un bug caché — elle peut entrer en collision avec une autre clé sans que
personne ne le remarque immédiatement. Le préfixe `auth.` est un namespace de fait.

**Sur l'importance des labels UX même dans une interface admin.** Une interface d'administration
n'est utilisée que par quelques personnes — mais ces personnes l'utilisent souvent. Un label
ambiguë qu'on voit dix fois par jour finit par agacer ou pire, induire en erreur. "Mot de passe"
est exact. "Code d'accès" est poétique mais flou dès qu'un autre "code" apparaît dans le même
tunnel d'authentification.
