## Contexte général

## Le problème de départ : appeler une API tierce depuis le front

### Deux raisons pour lesquelles c'est une mauvaise idée

**1. CORS.** Le navigateur refuse les requêtes cross-origin que le serveur cible n'autorise pas
explicitement. ipapi.co a des politiques CORS variables selon le plan tarifaire. On l'apprend
au pire moment — en production, devant un utilisateur.

**2. Rate limiting.** En free tier, ipapi.co limite à 1 000 requêtes/jour. Chaque visiteur unique
consomme un quota. Avec un peu de trafic (ou des bots), on décroche une 429 dès le lendemain.
Et là, tous les visiteurs voient l'overlay planté, sans aucune dégradation gracieuse côté front.

### Ce qu'on a fait à la place

Proxy côté serveur. Le front appelle `/api/geo` (une route Laravel locale, donc jamais de problème
CORS). Laravel interroge l'API tierce — et met le résultat en cache Redis. Résultat :
- Un visiteur → un appel API maximum (grâce au cache).
- Si l'API upstream est en rade : les requêtes en cache passent toujours ; les nouvelles IPs dégradent
  gracieusement (l'overlay s'affiche sans données de localisation).
- Changement de provider un jour ? On touche une variable d'environnement, pas le front.

En passant, on a changé de provider : ip-api.com est moins restrictif en free tier qu'ipapi.co.

## L'architecture : pourquoi un Service dédié

La première version du contrôleur `GeoController` avait commencé à grossir. Résolution de l'IP,
détection des adresses privées, appel HTTP, cache… Tout s'entassait dans `__invoke()`. C'est à ce
moment-là que l'on a posé la question qui s'impose.

**Est-ce qu'un contrôleur a vocation à contenir de la logique métier ?**

Non. Un contrôleur, c'est un orchestrateur. Il reçoit une requête HTTP, il délègue à un service, il
retourne une réponse. Trois lignes, idéalement. S'il commence à manipuler des adresses IP et à faire
des appels HTTP, c'est que quelque chose ne va pas.

On a donc extrait tout ça dans `GeoService`. Le contrôleur est redevenu ce qu'il aurait toujours dû
être :

```php
public function __invoke(Request $request): JsonResponse
{
    $data = $this->geo->locate($request->ip());
    return response()->json($data ?? ['error' => true]);
}
```

Trois lignes. Aucune logique métier. Testable uniquement via Feature tests HTTP — ce qui est suffisant
pour un code aussi simple.

## La méthode `resolveIp()` : un cas d'école de responsabilité

Pendant le développement, on a remarqué que l'IP détectée en local est toujours `127.0.0.1`. L'API
geo ne sait pas quoi faire d'une adresse loopback. Solution : permettre de configurer une IP publique
de substitution via `GEO_DEV_FALLBACK_IP`.

La logique de détection — *"est-ce une IP publique ? sinon, a-t-on un fallback ?"* — était apparue
en premier dans le contrôleur. Ce qui a immédiatement posé un problème : **cette logique est métier,
pas HTTP**. Elle doit vivre dans le service, pas dans la couche qui gère les requêtes HTTP.

Raisons concrètes :
- Un contrôleur qui fait de la détection d'IP ne peut pas être testé unitairement (il faut simuler
  une requête HTTP complète).
- Demain, si on appelle `GeoService` depuis un job de queue ou une commande Artisan, le contrôleur
  ne sera pas là pour faire ce boulot.

La méthode `resolveIp()` est maintenant `private` dans `GeoService`. Le contrôleur ne la connaît
même pas.

## Tests unitaires : le service sans dépendances externes

Un des critères de conception du `GeoService` : il doit être **intégralement testable unitairement**,
sans serveur HTTP, sans vraie base Redis, sans appel réseau réel.

Cela a imposé une contrainte d'architecture : **pas de dépendances non mockables dans le service**.
On n'injecte pas un client HTTP concret, on utilise la facade `Http::` de Laravel — que les tests
peuvent court-circuiter via `Http::fake()`. Idem pour `Cache::` et `Log::`.

Résultat : `GeoServiceTest` couvre 12 chemins d'exécution distincts, sans toucher le réseau ni Redis :
- IP nulle, IP privée sans fallback, IP privée avec fallback configuré
- Cache hit (success cache)
- Negative cache hit (on évite de re-taper une API en rade)
- Fetch → non-2xx HTTP
- Fetch → réponse invalide (`status: 'fail'` chez ip-api.com)
- Fetch → exception réseau
- Fetch → succès, mise en cache

Chaque cas d'erreur a son assertion sur les logs (`Log::assertLogged()`), pas seulement sur la valeur
de retour. On vérifie que les bonnes traces sont émises, pas seulement que le code ne plante pas.

L'ambition : **100 % de couverture sur la couche Service**. C'est là que vit la logique ; c'est là
que la couverture a de la valeur. Les contrôleurs, les providers, les modèles — testés différemment
(Feature tests, intégration DB) — sont délibérément exclus du calcul de couverture unitaire.

## Le double cache : success cache + negative cache

Un détail d'implémentation qui mérite une mention : la notion de *negative cache*.

Sans ça, un pic de trafic avec l'API upstream en 429 génère autant de tentatives que de requêtes.
Chaque visiteur déclenche un appel HTTP voué à l'échec. C'est exactement ce qui aggrave le rate
limiting.

Avec le negative cache (TTL de 60 secondes) : dès que l'API répond par une erreur, on enregistre
l'échec dans Redis. Pendant 60 secondes, toutes les nouvelles IPs reçoivent `null` directement, sans
aucun appel réseau. L'API upstream reprend son souffle, les logs ne s'affolent pas.

Le success cache (24 h) reste distinct : une IP déjà résolue avec succès continue à être servie
même si l'API est en rade. Les deux niveaux sont indépendants.

## Logging : pourquoi fixer un format dès le début

Les logs, c'est la dernière chose à laquelle on pense quand on démarre un projet. Et c'est l'une des
premières qu'on regrette de ne pas avoir faite correctement.

On a posé deux règles dès maintenant, formalisées dans `docs/logging-conventions.md` :

**1. Messages statiques.** Pas d'interpolation de variable dans le message de log. Le message est
toujours le même pour un même événement ; les données variables vont dans le tableau de contexte.

```php
// ✅
Log::error('Geo API fetch threw an exception', ['ip' => $ip, 'exception' => $e]);

// ❌
Log::error("Geo API fetch failed for IP {$ip}: " . $e->getMessage());
```

Raison concrète : avec un agrégateur de logs (Loki, Graylog, Datadog…), les messages statiques
permettent de **grouper des événements identiques**. Un message interpolé génère une entrée unique
par valeur d'IP — impossible à aggréger, impossible à alerter dessus.

**2. Contexte structuré obligatoire.** Chaque appel à `Log::` doit inclure `service`, `method`, et
`step`. Ces trois clés permettent de localiser immédiatement le code source d'un log, sans avoir à
grep le dépôt.

C'est un investissement de 30 secondes par appel de log. Le retour sur investissement se mesure la
première fois qu'on doit debugger un problème de prod à 23h.

## Ziggy : plus de routes en dur dans le JavaScript

Avant cette session, `boot.js` contenait en dur la chaîne `'https://ipapi.co/json/'`. Problème évident
quand on a switché sur le proxy Laravel : il a fallu changer l'URL. Mais surtout — hard-coder une URL
dans du JS dans un projet Laravel, c'est ignorer l'infrastructure de routing qui existe déjà.

Ziggy (`tightenco/ziggy`) expose les routes nommées Laravel côté JS via un helper `route()` injecté
par Blade. Au lieu de `'/api/geo'`, on écrit `route('api.geo')`. La route peut changer de préfixe,
être versionnée — le JS n'a rien à changer.

Corollaire dans les tests Vitest : `route()` n'existe pas en environnement de test (c'est une
injection runtime Blade). On le mock en une ligne :

```js
vi.stubGlobal('route', vi.fn().mockReturnValue('/api/geo'));
```

## Ce qu'on a corrigé en chemin (les détours instructifs)

- **PCOV ne peut pas être activé via `<ini>` dans phpunit.xml.** L'extension est de niveau système
  (`PHP_INI_SYSTEM`), pas modifiable à runtime. Solution : passer `-d pcov.enabled=1` directement
  sur la ligne de commande. On a encapsulé ça dans `scripts/check-coverage.php`.

- **PHPUnit 12 n'a plus l'attribut `coverageMinimumLinePercent` sur `<source>`.** La threshold de
  couverture doit être gérée en dehors du XML. D'où le script PHP qui parse le rapport Clover et
  sort avec un code non-nul si le seuil n'est pas atteint — branché sur le pre-commit hook.

- **`App\Models\User` apparaissait à 0% de couverture.** Le modèle était dans le scope sans l'avoir
  voulu. On a explicitement exclus `app/Models/`, `app/Http/Controllers/`, et `app/Providers/` du
  périmètre de couverture unitaire. Ces classes sont couvertes autrement (Feature tests).
