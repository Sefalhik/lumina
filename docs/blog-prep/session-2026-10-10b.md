## 2. Ce qu'une clé peut faire, pas où elle est rangée

Une clé SSH telle qu'on la génère ouvre un shell complet sur le compte : le `.env`, donc le mot de
passe de la base et `APP_KEY`. La ranger dans un secret GitHub ne change rien à ce qu'elle permet
le jour où elle fuit.

Le choix a donc été de borner **ce qu'elle autorise**, des deux côtés.

Côté serveur, une ligne d'`authorized_keys` :

```
command="/usr/bin/env bash …/scripts/deploy-gate.sh",restrict ssh-ed25519 …
```

`restrict` refuse terminal et redirections de port. `command="…"` force l'exécution d'un seul
script, quoi que demande l'appelant ; la demande arrive dans `SSH_ORIGINAL_COMMAND`. Ce script — la
« porte » — n'en honore que deux : `php-version`, et `deploy <sha>`.

Et c'est sur ce `<sha>` que tout s'est joué :

- **la forme ne suffit pas.** Le dépôt est public : GitHub sert le commit de n'importe quel fork,
  par son SHA, depuis l'adresse du dépôt. La porte ne récupère que `refs/heads/main` et demande à
  git si le commit en est un ancêtre ;
- **un commit de `main` n'est pas inoffensif parce qu'il a été relu un jour.** Celui d'avant un
  correctif, c'est la faille elle-même. La porte refuse tout commit plus ancien que celui qui est
  servi. Revenir en arrière reste une décision humaine, à la main ;
- **un commit d'avant les scripts emporterait la porte avec lui** : la clé ne répondrait plus à
  rien. Refusé aussi ;
- **`[0-9a-f]` n'est pas une liste de seize caractères.** Sous une locale UTF-8, bash lit la plage
  par collation : elle accepte `é` et les chiffres d'autres écritures. Or la locale est justement
  ce qu'un client SSH a le droit d'envoyer. Le motif énumère désormais ses caractères, et le test
  échoue bruyamment si la locale de la machine n'élargit pas les plages — sinon il ne prouverait
  rien.

Côté GitHub : la clé est un secret d'**environnement**, lisible seulement par un job qui nomme
l'environnement, lequel n'accepte que `main`. La clé d'hôte du serveur est épinglée ; le workflow
n'exécute jamais `ssh-keyscan`. Il n'utilise **aucune action**, pas même celles de GitHub : `ssh`
est déjà sur le runner. Jeton : `permissions: {}`. Une seule entrée, une liste fermée de deux mots.

Une clé volée peut donc faire avancer le serveur le long de `main`. Rien d'autre.

**Piste d'article** : « où est stocké le secret » est la question facile. « Que peut-on faire
avec » est celle qui compte le jour de la fuite.

## 3. Les réglages du dépôt, resserrés pour l'occasion

Tant qu'à écrire un workflow sans action, autant que le dépôt l'exige des autres : liste fermée
d'actions autorisées, épinglage par SHA obligatoire, approbation requise pour les PR de fork,
jeton en lecture par défaut.

Ce qui n'avait pas pu être mesuré le jour même — CodeQL est un workflow que GitHub gère, on ne le
lance pas à la main — l'a été le soir, sur la PR suivante : il passe.

## 4. « Aucune survivante », parmi celles que j'avais choisies

La question de Laurent, avant d'aller plus loin : *les tests sont-ils à la hauteur de ma
doctrine ?* La réponse honnête demandait une autre méthode que celle qui avait produit le chiffre.

Jusque-là, les mutations étaient **choisies à la main** : j'écrivais un test, puis la mutation qui
le faisait rougir. Le biais est dans la phrase. Une passe **mécanique** — supprimer chaque ligne
du fichier, une à une, et relancer les tests — n'a pas d'auteur.

| Fichier | Mutations choisies | Passe mécanique, avant correction |
|---|---|---|
| `deploy.yml` | toutes tuées | **16 suppressions sur 63** non remarquées |
| `update-frankenphp.sh` (LUMN-74, déjà mergé) | « 97, aucune survivante » | **36 sur 193** non remarquées |

Le workflow était testé comme du texte : des expressions régulières sur le YAML, aveugles à sa
structure. Les tests lisent maintenant le plan du fichier, et exécutent le script de l'étape contre
des doublures de `ssh` et de `rm`.

Pour LUMN-74, la passe a trouvé de vrais défauts de test, et un défaut de code : sous `pipefail`,
la lecture de la version installée faisait sortir le script en silence. Le ticket était mergé ; la
réparation est partie dans une PR sans clef, titrée **`[HORS-TICKET]`** — un quatrième cas écrit
dans `docs/git-workflow.md`.

L'outil est versionné : `node scripts/mutate-lines.js <fichier> -- <commande de test>`. Il refuse
une commande qui échoue déjà, garde une copie du fichier, et le restaure s'il est interrompu.

Après correction, sur les quatre fichiers de LUMN-50 :

| Fichier | Ciblées | Mécanique : non remarquées |
|---|---|---|
| `deploy.sh` | 38 / 38 | 0 sur 21 |
| `deploy-gate.sh` | 64 / 64 | 1 sur 48 (`local served`) |
| `deploy.yml` | 54 / 54 | 1 sur 62 (`;;`) |
| `check-deploy-key.sh` | 68 / 68 | 1 sur 110 (`set -euo pipefail`) |

**Piste d'article** : « aucune mutation n'a survécu » ne dit rien tant qu'on ne sait pas qui a
choisi les mutations.

## 6. La sonde qui a refusé une bonne clé

Les tests de la porte prouvent ce qu'elle fait d'une demande. Ils ne peuvent pas prouver que sshd
lui remet **toutes** les demandes : cela dépend d'une ligne tapée à la main sur le serveur.
`scripts/check-deploy-key.sh` mesure donc la clé de l'extérieur, avant que GitHub la voie : une
chose doit marcher, sept doivent être refusées. Elle n'affiche jamais ce qu'elle reçoit — une clé
mal restreinte montrerait ce qu'elle a atteint.

Premier passage sur le vrai serveur : six ✔, deux ✘. Terminal accordé, sftp non refusé.

La ligne d'`authorized_keys` était juste. C'est la sonde qui attendait des réponses que j'avais
**inventées** en écrivant sa doublure :

- **le terminal.** J'avais écrit : sshd refuse le terminal, puis exécute quand même la commande
  forcée. Faux pour `ssh -tt` : demandé explicitement, le terminal refusé est une erreur fatale
  côté client. `ssh` le dit, sort en 255, et **n'envoie jamais la commande**. La porte n'entend
  rien de cette sonde ;
- **sftp.** La porte s'exécute bien à la place du sous-système. Mais sshd jette la sortie d'erreur
  d'un sous-système : son « Refused: » n'arrive jamais. Il ne revient que son code de sortie, 1 —
  là où un vrai serveur sftp, sur une entrée vide, sort en 0 tout aussi silencieusement.

Les 40 tests de la sonde étaient verts, et ses mutations tuées. Ils prouvaient que la sonde jugeait
correctement **ma doublure**. Aucun ne pouvait dire que la doublure ressemblait au serveur.

La sonde juge maintenant ces deux cas sur ce qui revient vraiment. Et sous chaque ✘, elle dit ce
qu'elle attendait et ce qu'elle a observé : un code de sortie et le **nom** des phrases qu'elle
cherche, jamais la réponse. Avec ces deux lignes, le premier passage se serait expliqué tout seul.

Second passage, le dimanche matin : huit ✔.

**Piste d'article** : une doublure écrite avant la mesure est une hypothèse. Tant que le vrai
système n'a pas répondu, les tests ne vérifient que la cohérence de l'hypothèse avec elle-même.

## 7. Trois instruments faux en une nuit

Le plus instructif n'est pas la sonde. C'est la suite.

**Le diagnostic.** Pour comprendre les deux ✘, cinq commandes à lancer à la main. La troisième
finissait par `echo; echo "exit=$pipestatus[1]"`. Le `echo` intercalé avait déjà remplacé le
statut : elle a affiché `exit=0`, celui du `echo`. Pendant quelques heures, « sftp sort en 0 » a
été un fait mesuré — et c'était exactement la signature d'un sftp **ouvert**.

**L'horloge.** La passe mécanique, lancée en arrière-plan le soir, « tournait depuis sept heures
trente » au matin. Ni plantée ni en boucle : le portable avait dormi. `CLOCK_BOOTTIME` moins
`CLOCK_MONOTONIC` donnait 7 h 21 de veille ; la passe elle-même avait travaillé un quart d'heure.

**Le fichier.** Puis la passe ciblée, relancée — et, dans le même message, « tu peux relancer la
sonde ». Laurent l'a relancée pendant que la passe réécrivait le script toutes les quelques
secondes. Bash lit un script au fil de l'exécution : six ✔, puis une erreur de syntaxe ligne 174.
Les six ✔ ne valaient rien non plus. Certaines mutations consistent précisément à faire passer une
sonde quoi qu'il arrive.

Les trois ont la même forme : un résultat lu sans vérifier dans quel état était l'outil qui le
produisait.

**Piste d'article** : un test de mutation modifie le fichier qu'il teste. Pendant ce temps-là, ce
fichier n'est pas le vôtre.

## Pistes d'articles

- **L'instrument aussi se trompe.** Une sonde, un diagnostic, une horloge, un fichier en cours de
  mutation : quatre mesures fausses, une seule chose mesurée qui allait bien.
- **Ce qu'une clé peut faire, pas où elle est rangée.** Commande forcée, `restrict`, et une porte
  qui ne connaît que deux mots.
- **Sur un dépôt public, un SHA n'est pas un commit du projet.** Les forks, servis depuis la même
  adresse, et la question à poser à git.
- **Le vieux commit de `main` est une faille relue.** Pourquoi un pipeline ne doit pas savoir
  reculer.
- **`[0-9a-f]` et la locale.** Seize caractères en C, bien davantage en UTF-8, et l'appelant
  choisit.
- **Qui a choisi les mutations ?** 97 sans survivante, puis 36 sur 193 par une passe sans auteur.
- **La doublure qui n'avait jamais vu le serveur.** Quarante tests verts sur une hypothèse.
- **Un `echo` de trop.** Le code de sortie d'une autre commande, pris pour une mesure pendant une
  nuit.
