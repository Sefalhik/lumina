## Partie 1 — Le crash de `i18n:translate` sur `validation.php`

### Le symptôme

```
ErrorException: Array to string conversion
at app/Console/Commands/I18nTranslate.php:123
```

La commande plantait dès qu'elle atteignait `lang/fr/validation.php`. Pas sur `nav.php`,
pas sur `auth.php`. Uniquement sur `validation.php`.

### La cause

`validation.php` est le seul fichier de traduction Laravel qui contient des tableaux imbriqués —
en particulier la clé `attributes` qui mappe les noms de champs à leurs libellés humains :

```php
return [
    'required' => 'Le champ :attribute est obligatoire.',
    'attributes' => [
        'email' => 'adresse e-mail',
        'name'  => 'nom',
    ],
];
```

Le code original faisait :

```php
$flatSource = array_map('strval', $source);
```

`strval()` sur un tableau → `Array to string conversion`. Fatal.

### La solution en deux temps

**Temps 1 : le crash** — remplacer `array_map('strval', ...)` par `$this->flattenJson($source)`,
une méthode récursive déjà présente dans la classe qui produit des clés en notation pointée :

```php
// Entrée
['attributes' => ['email' => 'adresse e-mail']]
// Sortie
['attributes.email' => 'adresse e-mail']
```

**Temps 2 : la sortie** — `writePhpFile()` écrivait un tableau PHP plat, ce qui aurait produit :

```php
return [
    'required' => '...',
    'attributes.email' => '...',   // ← clé littérale avec un point, pas imbriquée
];
```

Techniquement acceptable pour Laravel (`Arr::get` gère les deux), mais visuellement incohérent
avec la source. Correction : appeler `unflattenJson()` avant d'écrire, puis utiliser un renderer
récursif `exportPhpArray()` qui produit la structure imbriquée correcte.

**Ce qu'on apprend** : un tableau PHP peut passer comme "source simple" dans tous les cas de test
tant qu'on ne teste qu'avec `nav.php`. Ajouter un test avec un fichier imbriqué (`validation.php`
simulé) aurait révélé le bug avant la prod. C'est un bel exemple de couverture insuffisante
malgré un bon taux de coverage global — le coverage mesure *quelles lignes* sont exécutées,
pas *avec quels types de données*.

## Partie 2 — Le JSON invalide silencieux : `max_tokens` trop petit

### Le symptôme

```
Invalid JSON in API response for locale bg
Invalid JSON in API response for locale cs
```

Et aucun log associé dans les fichiers Laravel — l'erreur s'affichait en console, disparaissait
dans le vide en environnement schedulé.

### Deux problèmes distincts

**Problème 1 : `max_tokens: 2048`** — `validation.php` contient environ 80 clés avec des messages
longs. La réponse JSON traduite dépasse facilement 2 048 tokens. L'API retourne alors un JSON
tronqué avec `stop_reason: max_tokens`. Un JSON tronqué n'est pas du JSON valide. Correction :
passer à `8192` (le maximum d'output pour Claude Haiku).

**Problème 2 : pas de logs** — les erreurs d'API n'étaient signalées qu'avec `$this->error()`,
qui écrit sur la sortie console. En tâche planifiée, cette sortie disparaît. Correction : ajouter
`Log::error()` structuré sur chaque chemin d'échec, avec `stop_reason` dans le contexte pour
diagnostiquer précisément ce qui s'est passé.

**Ce qu'on apprend** : une commande Artisan sans logging structuré est une boîte noire dès
qu'elle est schedulée. La règle doit être systématique : chaque chemin d'erreur doit écrire dans
les logs *en plus* de la console. La console est pour le développeur interactif. Les logs sont
pour le système de monitoring.

## Partie 3 — Extraction de `AnthropicTranslator` : le bon moment pour refactorer

### Le contexte

En concevant `cms:translate`, il devenait évident que `I18nTranslate` contenait trois
responsabilités mélangées :
1. L'appel API Anthropic (prompt, HTTP, parse de la réponse)
2. Les helpers JSON (flatten/unflatten)
3. L'orchestration fichiers (lecture, écriture, cache, checksum)

La responsabilité 3 est spécifique aux fichiers. Les responsabilités 1 et 2 sont génériques et
doivent être partagées.

### Le service `AnthropicTranslator`

```php
class AnthropicTranslator
{
    public function __construct(
        private readonly string $apiKey,
        private readonly string $model,
        private readonly array $nativeNames,
    ) {}

    public function translate(array $flatSource, string $locale): ?array { ... }
    public function flattenJson(array $array, string $prefix = ''): array { ... }
    public function unflattenJson(array $flat): array { ... }
}
```

Contrat minimal : reçoit des paires `clé → valeur` en français, retourne les paires traduites
ou `null` en cas d'erreur (avec log structuré dans le service).

Le binding dans `AppServiceProvider` utilise une closure lazy pour que les valeurs de config
soient lues au moment de la résolution, pas à l'enregistrement :

```php
$this->app->bind(AnthropicTranslator::class, fn () => new AnthropicTranslator(
    apiKey: (string) config('services.anthropic.api_key', ''),
    model: (string) config('services.anthropic.model', 'claude-haiku-4-5-20251001'),
    nativeNames: config('i18n.native_names', []),
));
```

**Décision sur les erreurs** : le service *log* les détails (HTTP status, `stop_reason`, extrait
du JSON invalide). La commande *affiche* un message générique (`Translation failed for locale de`).
Cette séparation est intentionnelle : la console est pour l'opérateur humain, les logs sont pour
le système de monitoring. Mélanger les deux (afficher des détails techniques en console) brouille
les responsabilités.

**Ce qu'on apprend** : le bon moment pour extraire un service n'est pas "quand c'est trop gros",
c'est "quand un second appelant apparaît". Un seul appelant peut justifier le report. Deux
appelants légitiment l'extraction immédiate.

## Partie 4 — `TranslationCache` étendu pour les contenus CMS

### La contrainte

`TranslationCache` gère deux niveaux de cache pour les fichiers :
- Checksum du fichier source (SHA-256) → skip si le fichier n'a pas changé
- Cache par clé avec TTL → skip si la traduction est encore fraîche

Pour les contenus CMS en base de données, il n'y a pas de fichier à hasher. Il faut détecter
le changement différemment.

### La solution

Deux nouvelles méthodes qui s'appuient sur le même stockage `checksums.json` :

```php
// Retourne les champs dont la valeur FR a changé depuis le dernier snapshot
public function getChangedCmsFields(string $cacheKey, array $frValues): array

// Persiste les valeurs FR comme référence après traduction
public function snapshotCmsRecord(string $cacheKey, array $frValues): void
```

La clé de cache est une chaîne arbitraire comme `cms_HomepageContent_1`. Le fichier
`checksums.json` ne distingue pas entre un chemin de fichier et une clé CMS — c'est
intentionnel, la structure est réutilisée.

La détection de changement compare les *valeurs* FR (pas un hash de fichier) :
si `frValues['tagline'] !== previousSnapshot['tagline']` → le champ a changé, il faut le
retraduire.

**Ce qu'on apprend** : réutiliser une primitive de stockage existante pour un nouveau cas d'usage
est souvent préférable à créer une nouvelle infrastructure. Le risque est de sur-abstraire ; ici
le concept ("snapshot d'une source de vérité") est suffisamment générique pour s'appliquer aux
deux cas.

## Partie 5 — `cms:translate` : conception de la commande

### Les décisions de design

**Cache key par enregistrement** : `cms_{ModelBaseName}_{id}`. Exemple : `cms_HomepageContent_1`.
Granularité suffisante pour que deux enregistrements différents n'interfèrent pas.

**Ajout d'un modèle** : uniquement une ligne dans `config/i18n.php` → `cms_models`. Pas de
modification de commande, pas de migration.

```php
'cms_models' => [
    \App\Models\HomepageContent::class,
    // \App\Models\ProjectCard::class,  // futur
],
```

**Guard `method_exists`** : `getTranslation` et `setTranslation` sont vérifiés par `method_exists`
avant d'être appelés. Cela permet d'enregistrer un modèle sans `HasTranslations` sans faire
crasher la commande — le comportement dégradé gracieux (`getAttribute` / `save` sans translation)
est préférable à une exception non gérée.

**`--dry-run` strict** : aucun appel API, aucune écriture en base, aucun snapshot de cache.
La commande liste ce qu'elle *ferait*. Utile pour valider la configuration avant un premier run.

### Le flow par enregistrement

```
Pour chaque record :
  1. Extraire les valeurs FR de chaque champ translatable
  2. Calculer les champs modifiés (delta vs snapshot)
  3. Pour chaque locale cible :
     a. Identifier les clés manquantes en cache
     b. Appeler l'API uniquement pour (delta ∪ manquantes)
     c. Écrire en cache
     d. Lire le cache complet
     e. setTranslation() + save()
  4. Snapshot des valeurs FR (référence future)
```

## Partie 6 — Observabilité des commandes Artisan schedulées

### Le constat

`I18nTranslate` et `CmsTranslate` n'avaient aucun `Log::` au moment de leur sortie de dev.
En lancement manuel, `$this->error()` suffit — on voit la sortie console. En tâche planifiée
(Laravel Scheduler, cron), cette sortie disparaît. Une commande qui échoue silencieusement est
une commande qui n'existe pas du point de vue du monitoring.

### Ce qui a été ajouté

Pour les deux commandes, le même pattern :

| Niveau | Quand |
|--------|-------|
| `Log::info` | Début du run (locales ciblées, flags actifs) |
| `Log::info` | Fin du run (succès/échec global) |
| `Log::debug` | Source inchangée, skippée |
| `Log::warning` | Source invalide, skippée |
| `Log::info` | Fichier/record traduit avec succès |
| `Log::error` | Traduction incomplète (nb clés reçues ≠ attendues) |
| `Log::error` | Appel API en échec |
| `Log::error` | Classe de modèle introuvable |

Les logs d'erreur API (`stop_reason`, extrait du JSON invalide) sont dans `AnthropicTranslator`,
pas dans les commandes. Les commandes ne logent que les événements d'orchestration.

**Ce qu'on apprend** : concevoir une commande Artisan "pour le scheduler" dès le départ, c'est
se demander : "si cette commande échoue à 3h du matin, comment je le saurai ?". La réponse est
dans les logs, pas dans la console.

## Partie 7 — Tester l'intestable : `BareTranslatableModel` et `Schema::create` en test

### Le problème

`CmsTranslate` contient une branche défensive :

```php
$val = method_exists($record, 'getTranslation')
    ? $record->getTranslation($field, 'fr', false)
    : $record->getAttribute($field);
```

Cette branche `false` (modèle sans `HasTranslations`) est un chemin critique — elle empêche un
crash si quelqu'un ajoute un modèle mal configuré dans `cms_models`. Mais comment la tester
sans créer un modèle de production qui ne soit pas translatable ?

### La solution : un modèle local dans le fichier de test

```php
// Hors de la classe de test, en bas du fichier
class BareTranslatableModel extends Model
{
    protected $table = 'bare_translatable_models';
    public array $translatable = ['title'];
    protected $fillable = ['title'];
}
```

Et dans le test, création + destruction de la table à la volée :

```php
public function test_uses_get_attribute_when_model_lacks_has_translations(): void
{
    Schema::create('bare_translatable_models', function ($table) {
        $table->id();
        $table->string('title')->nullable();
        $table->timestamps();
    });

    try {
        BareTranslatableModel::create(['title' => 'Mon titre']);
        config(['i18n.cms_models' => [BareTranslatableModel::class]]);
        // ...
    } finally {
        Schema::dropIfExists('bare_translatable_models');
    }
}
```

Le `try/finally` garantit la suppression de la table même si le test échoue. `RefreshDatabase`
ne suffit pas ici — il ne supprime que les données, pas les tables créées dynamiquement.

**Ce qu'on apprend** : définir un modèle minimal dans un fichier de test est une technique
parfaitement légitime en PHPUnit. Ce n'est pas "sale" — c'est isolé, explicite, et ne pollue
aucun modèle de production. `Schema::create/drop` en test est le seul moyen propre de tester
des chemins qui dépendent de la structure du modèle plutôt que de ses données.

## Sujets d'articles potentiels

### Articles techniques

1. **"PHP + Anthropic API : traduire 24 langues sans exploser sa facture"**
   Stratégie de cache à deux niveaux (checksum de fichier + TTL par clé), `max_tokens` à calibrer
   selon la taille du payload, `stop_reason: max_tokens` comme indicateur de troncature, le prix
   réel d'un run complet vs. incrémental.

2. **"`array_map('strval', ...)` : le piège silencieux des tableaux imbriqués"**
   Court mais précieux. L'erreur `Array to string conversion` est opaque. La leçon : ne jamais
   supposer qu'un fichier PHP de traduction est plat — `validation.php` est le contre-exemple
   canonique. Introduire `flattenJson` / `unflattenJson` avec dot-notation comme pattern générique.

3. **"Artisan commands et observabilité : `$this->error()` ne suffit pas"**
   Anatomie d'une commande schedulée qui échoue silencieusement. Distinction console (opérateur
   humain) vs logs (monitoring). Pattern de logs structurés : `service`, `method`, `step` comme
   contexte minimal. Intégration avec Telescope et/ou Sentry.

4. **"Service layer en Laravel : quand et comment extraire ?"**
   Le déclencheur naturel : l'apparition d'un second appelant. Avant : déférer l'extraction mais
   noter la dette. Après : extraire vers `app/Services/`. Exemple concret avec `AnthropicTranslator`
   partagé par `i18n:translate` et `cms:translate`. Bonus : le binding IoC avec closure lazy dans
   `AppServiceProvider`.

5. **"`spatie/laravel-translatable` en pratique : JSON multilingue avec PostgreSQL"**
   Comparaison des trois approches (table liée / colonne par langue / JSON unique). Pourquoi
   `setTranslation` (singulier) et pas `setTranslations` (pluriel) — le piège qui efface toutes
   les locales. Formulaire admin FR uniquement + traduction différée.

6. **"Tester une commande Artisan qui touche la base de données"**
   Isolation avec `RefreshDatabase`, rebind du service via `$this->app->bind()` dans les tests,
   `Http::fake()` pour mocker l'API externe, `Schema::create` pour les modèles de test ad hoc.
   Le pattern `BareTranslatableModel` pour couvrir les branches défensives.

7. **"Coverage à 80% ne signifie pas que vos bugs sont couverts"**
   Illustration avec `validation.php` : toutes les lignes de `I18nTranslate` étaient couvertes,
   mais uniquement avec des données plates. Le type de donnée est un vecteur de bug autant que
   le chemin de code. Plaidoyer pour des tests property-based ou des données de test diversifiées.

### Articles d'opinion / méthodo

8. **"Pourquoi je traduis mon site avec Claude plutôt qu'avec DeepL"**
   Contexte : 24 langues officielles UE, terminologie UI spécifique (placeholders, marques).
   DeepL et Google Translate sont bons sur le texte courant, moins sur le jargon technique et les
   placeholders. Claude comprend les instructions ("ne traduis pas les valeurs entre `{}`") et
   maintient la cohérence stylistique sur l'ensemble du payload. Coût comparatif.

9. **"La règle du service layer : aucune logique dans les contrôleurs, modèles, et composants Vue"**
   Règle dure. Exemples concrets des violations courantes. Pourquoi "c'est juste quelques lignes"
   est l'argument le plus dangereux en architecture. La testabilité comme proxy de la qualité
   architecturale.

10. **"Construire un site personnel en 2026 : pourquoi pas un CMS existant ?"**
    Réflexion sur le choix de développer un CMS léger sur Laravel plutôt d'utiliser WordPress,
    Strapi ou Contentful. Contrôle total sur le modèle de données, l'i18n et les performances.
    Complexité assumée en échange d'une maîtrise complète. Les moments où ce choix aurait pu
    être différent.
