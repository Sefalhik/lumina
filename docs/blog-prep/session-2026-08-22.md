## Contexte

Session partie d'une intention minimale — « lancer la mise à jour des dépendances Composer » — et qui a fini par traverser quatre sujets sans rapport apparent : le débogage d'une exception Laravel trompeuse, l'absorption d'un franchissement de version majeure non voulu sur la couche HTTP, la reconfiguration d'un board Jira qui n'affichait rien, puis l'implémentation des balises `hreflang` et `canonical` sur un site multilingue.

Le fil rouge, rétrospectivement : **quatre cas où le signal visible mentait sur la réalité sous-jacente.** Une trace qui désigne la mauvaise exception. Un `^` qui semble protéger et ne protège pas. ## `Target class [config] does not exist` — quand le handler d'exception masque l'exception

### Le symptôme

`composer update` échoue sur le hook `post-autoload-dump`, avec une trace de 80 lignes :

```
PHP Fatal error: Uncaught ReflectionException: Class "config" does not exist
  in vendor/laravel/framework/src/Illuminate/Container/Container.php:1145
...
#6  Illuminate\Log\LogManager->getDefaultDriver()
#10 Illuminate\Foundation\Exceptions\Handler->reportThrowable()
#13 Illuminate\Foundation\Console\Kernel->reportException()
Script @php artisan package:discover --ansi ... returned with error code 255
```

La tentation est de chercher pourquoi le binding `config` a disparu du container. C'est une impasse : **il n'a jamais disparu.**

### Lire la trace à l'envers

Les frames à regarder ne sont pas les premières, mais celles du milieu : `reportException` → `reportThrowable` → `LogManager->error()`. Cette séquence dit qu'une **autre** exception a été levée, et que Laravel a voulu la journaliser. Pour journaliser, `LogManager` doit résoudre le driver de log, donc lire `config('logging.default')`, donc résoudre `config` dans le container.

Or l'application n'avait pas fini de bootstrapper. Le container était vide. Le handler d'exception a donc planté en tentant de rapporter l'erreur — et c'est **son** crash qu'on voit, pas celui d'origine. L'exception réelle est avalée, définitivement.

C'est un mode de défaillance générique de tout framework à container : **quand le reporter d'erreur dépend du système qui a échoué, l'erreur réelle est perdue.**

### Démasquer l'exception réelle

Court-circuiter le handler en bootstrappant à la main, avec un `try/catch` qui n'utilise ni le container ni le logger :

```php
php -r '
require "vendor/autoload.php";
try {
    $app = require_once "bootstrap/app.php";
    echo "App bootstrapped OK\n";
    $kernel = $app->make(Illuminate\Contracts\Console\Kernel::class);
    $kernel->bootstrap();
    echo "Kernel bootstrapped OK\n";
} catch (Throwable $e) {
    echo "REAL ERROR: " . get_class($e) . "\n";
    echo $e->getMessage() . "\n";
    echo $e->getFile() . ":" . $e->getLine() . "\n";
}'
```

Résultat : **les deux bootstraps passent.** Puis `php artisan package:discover` seul : passe aussi. Puis `composer dump-autoload` : passe.

### Le diagnostic

Rien n'était cassé au moment du diagnostic. L'erreur était **transitoire** : le hook `post-autoload-dump` s'était exécuté pendant que Composer réécrivait `vendor/`, sur un arbre de dépendances momentanément incohérent — des paquets supprimés, d'autres pas encore écrits, un autoloader désynchronisé.

Ce `composer update` supprimait `ralouphie/getallheaders` et remplaçait toute la chaîne Guzzle. La fenêtre d'incohérence était donc large.

### Ce qu'il faut retenir

- Un `post-autoload-dump` qui échoue pendant un `composer update` massif n'indique pas forcément un problème réel — **relancer `composer dump-autoload` avant de diagnostiquer quoi que ce soit.**
- Vérifier `bootstrap/cache/` (config, packages, services) reste le premier réflexe, mais ici le répertoire était déjà vide.
- Quand une trace passe par `reportException` → `LogManager`, **l'erreur affichée n'est pas l'erreur réelle**. Bootstrapper à la main pour la retrouver.

## Guzzle 7 → 8 sans toucher à `composer.json` — le `^` ne protège pas de ce qu'on croit

### Le constat

Le `composer update` a fait franchir cinq versions majeures :

| Package | Avant | Après |
|---|---|---|
| `guzzlehttp/guzzle` | 7.15.2 | 8.0.2 |
| `guzzlehttp/promises` | 2.5.1 | 3.0.1 |
| `guzzlehttp/psr7` | 2.13.0 | 3.0.0 |
| `guzzlehttp/uri-template` | v1.0.10 | v2.0.0 |
| `hamcrest/hamcrest-php` | v2.1.1 | v3.0.0 |

Aucune ligne de `composer.json` n'a été modifiée. Le projet ne déclare pas Guzzle du tout.

### Pourquoi le garde-fou n'a pas joué

L'intuition commune est que `^` protège des majeures : `^7.0` n'ira jamais en 8.0. C'est vrai — **pour les dépendances qu'on déclare soi-même.**

Guzzle est ici une dépendance *transitive*, tirée par `laravel/framework`. Et c'est Laravel qui décide de sa fourchette :

```bash
$ composer why guzzlehttp/guzzle
laravel/framework v13.26.1 requires guzzlehttp/guzzle (^7.8.2 || ^8.0)
```

Laravel a élargi sa contrainte en amont, dans une version *mineure* (v13.23 → v13.26). Le `^13.0` du projet a donc laissé passer cette mineure, qui a elle-même autorisé une majeure transitive. La protection semver a fonctionné exactement comme spécifié — sur le mauvais niveau.

**Un `^` sur une dépendance directe n'est pas une protection contre les majeures de ses dépendances.** Le seul rempart réel est la relecture du diff de lockfile, ou un outil de veille qui isole les majeures dans des PR séparées.

### Détecter les majeures dans un diff de lockfile

Le diff brut fait 761 lignes — illisible. Un script de 15 lignes suffit à extraire le signal :

```python
import json, subprocess
def idx(d):
    r = {}
    for k in ('packages', 'packages-dev'):
        for p in d.get(k, []):
            r[p['name']] = p['version']
    return r

old = json.loads(subprocess.run(['git','show','HEAD:composer.lock'],
                                capture_output=True, text=True).stdout)
new = json.loads(open('composer.lock').read())
o, n = idx(old), idx(new)
major = lambda v: v.lstrip('v').split('.')[0]

for name in sorted(set(o) & set(n)):
    if o[name] != n[name] and major(o[name]) != major(n[name]):
        print(f"{name:45} {o[name]:12} -> {n[name]}")
```

Le même principe s'applique à `package-lock.json` (structure `packages` avec clés `node_modules/...`). Verdict côté npm ce soir : **zéro majeure**, 60 mises à jour mineures. Tout le risque était côté PHP.

## `Http::fake()` valide un contrat, jamais une joignabilité

### L'angle mort

La suite de tests couvre les deux services qui font des appels sortants (`AnthropicTranslator`, `GeoService`), avec une règle de projet stricte : **jamais d'appel HTTP réel en test**, tout passe par `Http::fake()`.

C'est la bonne règle — tests déterministes, rapides, sans dépendance réseau. Mais elle a une conséquence qu'un franchissement de majeure sur la couche transport rend soudain critique :

> `Http::fake()` intercepte **avant** que Guzzle n'entre en jeu. La suite valide donc que le code applicatif appelle correctement le client HTTP de Laravel — elle ne teste **jamais** Guzzle lui-même.

165 tests verts, 100 % de couverture, et pourtant **aucune preuve** que Guzzle 8 fonctionne.

### Le faux ami du `--dry-run`

Premier réflexe pour combler le trou : lancer les commandes de traduction en mode simulation.

```bash
php artisan i18n:translate --dry-run   # All translations completed.
php artisan cms:translate --dry-run    # All CMS translations completed.
```

Vert, mais **sans valeur** pour ce risque précis. Vérification dans le code avant de conclure quoi que ce soit :

```php
// app/Console/Commands/I18nTranslate.php:170
if ($this->option('dry-run')) {
    continue;                    // <- sort AVANT keysToTranslate()
}
$toTranslate = $this->keysToTranslate(...);  // <- l'appel HTTP est ici
```

Le `continue` intervient avant l'appel réseau. Le dry-run valide le bootstrap, la résolution des services et le cache de checksums — pas une ligne de Guzzle.

### La vérification qui compte

Un seul appel réel, hors test, à travers le vrai service applicatif :

```bash
php artisan tinker --execute="print_r(app(App\Services\GeoService::class)->locate('8.8.8.8'));"
```

HTTP 200, JSON décodé, et `$response->transferStats->getRequest()` de classe `GuzzleHttp\Psr7\Request` — confirmation que c'est bien la nouvelle chaîne PSR-7 3.0 qui travaille.

Choix délibéré de passer par `GeoService->locate()` plutôt que par un `Http::get()` nu : le service applique son propre cache, sa gestion d'erreur, son timeout. C'est ce chemin-là qui tourne en production, pas un appel de laboratoire.

### La généralisation

Une suite de tests entièrement mockée sur la couche transport a un angle mort structurel lors d'une montée de majeure de cette couche. **La réponse n'est pas d'assouplir la règle de mock** — c'est d'ajouter un critère d'acceptation distinct, exécuté manuellement, qui exerce le vrai transport une fois.

Formulé dans le ticket comme critère à part entière :

> 7. Un appel HTTP réel, hors test, aboutit sous Guzzle 8 — seul critère couvrant le risque réel de la montée en majeure.

## Jira — trois onglets, deux sources de vérité, zéro ticket affiché

### Le symptôme

Tous les tickets visibles dans l'onglet **Liste**. Onglet **Tableau** : colonnes affichées, aucun ticket. Onglet **Backlog** : 3 tickets sur 8.

### Les fausses pistes

Deux hypothèses successives, plausibles et fausses :

**1. Statuts non mappés aux colonnes.** Sur un projet company-managed, remplacer le workflow par défaut par un workflow personnalisé laisse les nouveaux statuts en « non mappés », et un ticket dans un statut non mappé n'apparaît sur aucune colonne. Explication cohérente… mais le mapping était correct.

**2. Statuts homonymes.** Le projet contenait deux `En cours` — celui du workflow (ID 10039) et le `En cours` système de Jira — indiscernables dans l'interface, qui n'affiche pas les IDs. Mapper le mauvais aurait produit une colonne vide. Piste sérieuse, invalidée en déclenchant une transition et en lisant l'ID de statut retourné par l'API : `10039`, le bon.

### La vraie cause

Le nom de l'onglet, lu littéralement : **« Sprint actif »**.

Le board avait été créé en **Scrum**, alors que la méthode de travail retenue est **Kanban, sans sprints, WIP à 1**. Sur un board Scrum, « Sprint actif » n'affiche que les tickets rattachés à un sprint **démarré**. Aucun sprint n'ayant jamais été créé, l'onglet était structurellement vide — indépendamment de tout mapping.

Et le backlog partiel s'explique de même : le backlog Scrum liste les items de travail, mais **les epics n'y figurent pas comme des lignes** (elles vivent dans le panneau latéral). Les 5 tickets manquants étaient les 5 epics. Rien n'était perdu.

Correctif : créer un board **Kanban** sur le même filtre. Jira ne convertit pas un board Scrum en Kanban — c'est une création, l'ancien board n'étant qu'une vue sur un filtre, sans donnée propre.

### Ce qu'il faut retenir

- Sur un projet company-managed, **Liste** interroge le projet ; **Tableau** et **Backlog** passent par un board et son mapping. Trois vues, deux sources.
- **Le type de board (Scrum/Kanban) prime sur le mapping.** Vérifier le type avant de déboguer les colonnes — le nom de l'onglet le trahit.
- Des statuts homonymes sont indiscernables dans l'UI. L'API, elle, retourne l'ID : c'est le seul moyen fiable de trancher.
- Corollaire organisationnel : **un outil de suivi configuré sur une méthode qu'on ne pratique pas ne remonte aucun signal** — il affiche du vide, ce qui se confond avec « rien à faire ».

## Le workflow GitHub → Jira, validé de bout en bout

### La chaîne

Deuxième validation complète, et première sur un ticket rattaché à une epic :

```
ticket créé (Backlog)
  → transition 2 (Préparer)      → Prêt
  → transition 3 (Démarrer)      → En cours
  → PR ouverte  ─ GitHub Actions → transition 4 → En review
  → PR mergée   ─ GitHub Actions → transition 5 → PR approuvée
```

### L'extraction de clé

```yaml
KEY=$(printf '%s\n%s' "$HEAD_REF" "$PR_TITLE" \
      | grep -oiE 'LUMN-[0-9]+' | head -1 | tr '[:lower:]' '[:upper:]')
```

Deux sources (branche **et** titre), insensible à la casse, normalisé en majuscules. Une branche `chore/lumn-8-update-dependencies` en minuscules suffit à déclencher la synchro — détail qui évite d'imposer une convention de nommage en majuscules, peu naturelle.

### Le piège de l'ordre des états

Une transition Jira n'aboutit **que depuis l'état source attendu**. La transition 4 part de `En cours` ; un ticket resté en `Backlog` la verrait refusée. D'où l'obligation de faire passer manuellement le ticket par `Prêt` puis `En cours` **avant** d'ouvrir la PR.

Et le workflow n'échoue jamais sur un refus :

```bash
echo "::warning::Transition 'Ouvrir PR' refusée pour $JIRA_KEY (HTTP $CODE)"
```

**Un run vert ne prouve donc pas que la synchronisation a fonctionné.** La seule vérification fiable est de relire le statut côté Jira — ce qui a été fait via l'API après chaque étape.

C'est une dette assumée : sur un pipeline personnel, un warning suffit ; sur un pipeline d'équipe, il faudrait faire échouer le job, sous peine de créer une confiance non fondée dans un indicateur vert.

### Le détail qui aurait bloqué

Deux comptes GitHub sur la même machine. Le compte actif (`gh auth status`) n'avait qu'un accès `READ` sur le dépôt — le `push` aurait échoué avec une erreur de permission, facilement mal interprétée comme un problème de token ou de remote. Un `gh auth switch --user <owner>` avant l'opération, et rien à déboguer.

## `hreflang` et `canonical` — le piège qui désindexe 19 langues

Le site existe en 24 langues officielles de l'UE, sans qu'aucune balise n'indique aux moteurs qu'il s'agit du même contenu traduit. Premier ticket concret de l'epic SEO.

### Faut-il vraiment exposer 24 langues ?

L'intuition initiale — la mienne — était le risque de sanction : 23 des 24 versions sont produites automatiquement par appel API, sans relecture humaine, et « Google pénalise la traduction automatique ». **Cette intuition est fausse, et il a fallu aller vérifier plutôt que la propager.**

L'état réel de la doctrine :

- La traduction automatique n'est pas du spam en soi. La politique *scaled content abuse* vise la production en masse de contenu sans valeur pour l'utilisateur, **pas la méthode de production**.
- Google a **retiré** son ancienne recommandation de bloquer les pages auto-traduites via `robots.txt`.
- Reddit traduit des millions de pages par IA, et Google l'assume publiquement.

Le vrai argument est ailleurs, et il est plus intéressant. Les moteurs actuels rapprochent les contenus équivalents entre langues au niveau sémantique et ne servent qu'une seule version d'un concept donné — généralement celle qui fait le plus autorité, souvent l'anglaise. **Une page traduite qui n'apporte ni intention nouvelle, ni contexte propre à un marché, n'est presque jamais servie.**

La ligne de partage n'est donc plus « traduit à la main » contre « traduit par machine », mais **contenu réellement adressé à un marché** contre **réplique traduite**.

Décision retenue : cinq locales déclarées — `fr`, `en`, `de`, `it`, `nl`. Non par crainte d'une pénalité, mais parce que déclarer 24 langues multiplie par 24 la surface à explorer pour un site sans autorité établie, sans rien rapporter.

### Deux listes, deux questions

Le point de conception qui compte : **restreindre l'indexation ne doit rien retirer au site.**

D'où deux clés de configuration distinctes, et la discipline de ne jamais les confondre :

- `supported_locales` (24) répond à « qu'est-ce que le site **sert** ? » — routage, sélecteur de langue, commandes de traduction
- `indexable_locales` (5) répond à « qu'est-ce que le site **déclare aux moteurs** ? » — `hreflang` uniquement

Un visiteur sur `/mt/` obtient toujours une page maltaise complète. Seule change la liste annoncée aux robots. La seconde liste doit rester un sous-ensemble de la première — garde implémentée, entrées hors périmètre filtrées à l'exécution et journalisées.

### Allowlist contre denylist — l'asymétrie des modes de défaillance

Les routes d'authentification et d'administration vivent sous le **même préfixe** `/{lang}/` que les pages publiques. Il faut donc décider quelles routes portent les balises.

Deux approches, et le choix ne se joue pas sur l'élégance mais sur ce qui arrive **quand on oublie** :

- **Liste blanche** — on oublie d'ajouter une nouvelle page publique : elle perd ses balises SEO. Silencieux, sans dommage, corrigé en une ligne.
- **Liste noire** — on oublie d'exclure une nouvelle route d'administration : **la structure d'URL de l'admin est publiée dans le `<head>` de chaque page du site.**

L'asymétrie tranche. C'est un principe qui dépasse largement le SEO : **quand deux conceptions sont équivalentes en fonctionnement nominal, celle qui échoue du côté inoffensif gagne.**

### `canonical` et `hreflang` ne suivent pas la même règle

Le piège le plus coûteux de ce ticket, et il n'apparaît qu'en y réfléchissant deux minutes de plus.

Le réflexe naturel, une fois qu'on a restreint l'indexation à 5 langues, est de faire pointer le `canonical` des 19 autres vers la version française — « puisque c'est la version de référence ». **Ce serait demander explicitement aux moteurs de retirer 19 langues de l'index.** Un `canonical` déclare « cette page est un doublon de celle-là ». Or une page maltaise n'est pas un doublon de la page française : c'est un contenu distinct, dans une autre langue.

Règle retenue : **le `canonical` est toujours auto-référent**, dans chaque locale servie, indexée ou non.

Le `hreflang`, lui, obéit à une contrainte inverse : **la réciprocité**. Chaque variante déclarée doit référencer toutes les autres, elle-même incluse. Une page dans une locale non indexée ne doit donc déclarer **aucun** `hreflang` : si `/mt/` listait les cinq locales indexées alors qu'aucune d'elles ne référence `mt` en retour, le groupe entier serait invalidé.

Le comportement final tient en trois lignes :

| Page | canonical | hreflang |
|---|---|---|
| Publique, locale indexée | auto-référent | 5 locales + `x-default` |
| Publique, locale non indexée | auto-référent | aucun |
| Auth / admin | aucun | aucun |

`x-default` pointe vers la racine `/`, déjà gérée par le résolveur de locale depuis l'en-tête `Accept-Language` — exactement sa sémantique : que servir quand aucune langue déclarée ne correspond au visiteur.

### Détail d'implémentation qui évite du câblage

La logique vit dans un service sans dépendance à la requête HTTP : on lui passe le nom de route et ses paramètres. Un *view composer* sur le layout principal alimente les variables du template.

Conséquence pratique : **aucun contrôleur n'a quoi que ce soit à câbler.** Une nouvelle page publique obtient ses balises en ajoutant son nom de route à la configuration, point final.

Piège traité au passage : les paramètres de route doivent être préservés lors de la substitution de locale. Une route d'article porte un `{slug}` — ne remplacer que `lang` en ignorant le reste produirait des URLs invalides pour toutes les pages de contenu.

### L'accroc PHPStan, corrigé à la source

Le test du journal utilisait `Log::spy()` puis `Log::shouldHaveReceived()`. L'analyse statique refuse : la façade relaie cette méthode via `__callStatic`, donc elle n'existe pas statiquement.

La tentation est le contournement — annotation de suppression, cast, ligne ignorée. Le projet l'interdit explicitement, et à raison : l'erreur signalait que ce test n'était pas écrit comme les autres. Le codebase avait déjà un motif pour ça, sans Mockery, à base d'écoute d'événements de log. S'y aligner a supprimé l'erreur **et** rendu le test cohérent avec ses voisins.

**Une erreur d'analyse statique est souvent un désaccord avec les conventions du projet, pas un obstacle technique.**

## Bilan

Session d'entretien puis de fondation SEO, qui a produit :

- Une exception Laravel opaque démasquée et comprise
- Cinq majeures absorbées, validées par 7/7 checks **et** un appel réel hors test
- Un ticket Jira documentant explicitement l'angle mort du mock HTTP
- Un board Kanban enfin fonctionnel, après deux fausses pistes
- La chaîne ticket → branche → PR → merge → Jira validée une deuxième fois
- Les balises `canonical` et `hreflang` en place, 20 tests, couverture à 100 %, conventions documentées

Sur les tickets qui s'accumulent en `PR approuvée` : les transitions de déploiement (6 et 7) ne sont pas implémentées, faute de production. La tentation est de lire ça comme un défaut de conception du workflow — c'était mon analyse, et elle est fausse.

L'état terminal n'est pas atteignable parce qu'**il n'y a rien à mettre en production** : sans balises SEO et sans contenu, il n'y a pas de première mise en ligne à faire. Un WIP gelé dans ces conditions ne trahit pas un système mal conçu, il décrit fidèlement la réalité. Automatiser un déploiement avant de savoir ce que l'hébergeur autorise reviendrait à construire la partie la plus délicate du pipeline dans le vide.

**Une limite de WIP qui bloque n'est pas toujours un symptôme à corriger — parfois c'est l'indicateur qui fonctionne.** La distinction est de savoir si le blocage vient du système ou de la réalité qu'il mesure.

- **Trois onglets, deux sources de vérité — déboguer un board Jira qui n'affiche rien** : Liste vs Tableau vs Backlog sur un projet company-managed, pourquoi le type de board prime sur le mapping des colonnes, les statuts homonymes indiscernables dans l'UI, et pourquoi les epics ne s'affichent pas dans un backlog Scrum. Récit de deux fausses pistes avant la bonne — format « enquête » qui se lit bien.

Angle méthode, avec une nuance qui fait tout l'intérêt du sujet — un WIP gelé n'est pas forcément un défaut à corriger, il peut être l'indicateur qui fait correctement son travail. Contre-intuitif, sourcé, très partageable.

Piège coûteux, court à expliquer, format idéal pour un article dense.

- **Allowlist ou denylist — choisir par le mode de défaillance, pas par l'élégance** : cas concret des routes SEO quand l'admin partage le préfixe des pages publiques. Oublier une entrée dans une liste blanche coûte du référencement ; l'oublier dans une liste noire publie la structure de l'admin. Principe transposable bien au-delà du SEO (permissions, filtres, feature flags). Angle conception défensive.

- **Une erreur PHPStan est souvent un désaccord avec les conventions du projet** : le cas `Log::shouldHaveReceived()` invisible pour l'analyse statique, la tentation de la ligne de suppression, et ce qu'on découvre en cherchant pourquoi le code existant ne déclenchait pas l'erreur. Court, mais bon angle sur la discipline d'équipe face aux outils d'analyse.
