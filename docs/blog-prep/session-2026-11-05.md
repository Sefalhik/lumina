# Session 2026-11-05 — La CI a changé de shell sans prévenir

## Contexte

Retour après treize jours sans activité. L'état des lieux : l'audit quotidien rouge depuis une
semaine (25 avis), et **toutes** les pull requests Renovate en échec — y compris celle qui ne
change qu'un digest Docker. Rien n'avait bougé sur `main` depuis LUMN-91.

---

## 1. Un seul test, partout le même

Derrière « la CI échoue partout », un seul test : `release.test.js`, le cas Ctrl-C des signaux
envoyés à tout le groupe de processus. Statut attendu 130 (128 + SIGINT), reçu 141 (128 + SIGPIPE).
HUP et TERM passaient.

Vert le 26/10, rouge à partir du 30/10, **sans aucun commit entre les deux**. Les journaux des
runners donnaient la réponse : `ubuntu-latest` était passé de 24.04 à 26.04. En local (Mint, base
24.04), le test passait 5 fois sur 5 ; dans un conteneur `ubuntu:26.04`, il échouait 3 fois sur 3.

**Piste d'article** : quand rien n'a changé dans le dépôt, regarder ce qui a changé autour.
`ubuntu-latest` est une dépendance comme une autre, sauf qu'aucun outil ne la surveille.

---

## 2. La fausse piste élégante

Ubuntu 26.04 livre les coreutils réécrits en Rust (uutils) : `tee` n'est plus celui de GNU. Le
suspect idéal, d'autant que le script repose sur `tee -p`. Il a été écarté en remplaçant une à une
`tee`, `cat`, `rm`, `mkdir` et `dirname` par leurs versions GNU, toujours présentes sous
`/usr/bin/gnu*` : le test échouait toujours.

Ce qu'il restait : bash, passé de 5.2 à 5.3.

---

## 3. `/proc` ne ment pas

Le script lance deux `tee` dans des substitutions de processus, `>( trap '' HUP INT TERM; exec tee … )`,
pour qu'ils survivent à un terminal qui raccroche et gardent les derniers mots du déploiement.
Sous bash 5.3, dans une telle substitution, `/proc/self/status` montre `SigIgn: 0x4005` : HUP,
QUIT et TERM ignorés — **pas INT**. Le même `trap` fonctionne dans un sous-shell ordinaire, et
partout sous bash 5.2. Le changelog de bash 5.3 n'en dit rien.

En creusant plus tard, le mécanisme exact est plus curieux encore. Bash 5.3 démarre une
substitution de processus comme une commande en arrière-plan : INT et QUIT y sont **déjà**
ignorés (`0x6`, contre `0x0` en 5.2). Et y écrire `trap '' INT` les **réactive** (`0x4`). Le trap
fait l'inverse de ce qu'il dit.

La suite est une cascade : Ctrl-C tue les `tee`, le rapport d'échec part dans un pipe sans lecteur,
SIGPIPE termine le script au milieu de son trap `EXIT` — avant la ligne du journal des déploiements.
**Un déploiement interrompu ne laissait plus aucune trace**, ni à l'écran, ni dans le fichier
conservé, ni dans le journal.

La correction : ne pas demander aux `tee` d'ignorer le signal une fois lancés, mais les lancer avec
le signal déjà ignoré. Ce qui est ignoré au démarrage d'un processus le reste à travers `exec`, dans
toutes les versions.

**Piste d'article** : le test qui a cassé la CI n'était pas instable, il avait raison. Figer la CI
sur 24.04 l'aurait remis au vert en cachant un vrai défaut du script de déploiement.

---

## 4. La passe mécanique trouve la ligne que je n'avais pas testée

La correction ignore les signaux dans le script parent, puis les rétablit aussitôt (`trap -`). La
passe de mutation a supprimé les 76 lignes du script une à une : une seule suppression est passée
inaperçue, ce `trap -`. Sans lui, un Ctrl-C arrivant entre le lancement des `tee` et la pose des
traps du script serait avalé, et le déploiement continuerait comme si de rien n'était.

Un faux `git`, qui envoie le signal à tout le groupe au moment où le script liste ses releases,
place l'interruption exactement dans cette fenêtre. Sans la ligne, le script sort en 0 : le test
rougit pour la bonne raison, sous bash 5.2 comme sous 5.3. Repassée dans le conteneur 26.04, la
passe mécanique ne laisse plus aucun survivant sur les 76 lignes.

Et le test d'origine vérifiait le statut et la sortie, pas la ligne du journal — justement celle
qui se perdait. Il la vérifie désormais, et cette assertion rougit seule sans la correction.

---

## 5. « On en est où, par rapport à la doctrine ? »

J'avais annoncé le travail fini. Laurent a posé la question, et le bilan honnête comptait trois
trous :

- **Le point que le ticket disait « à vérifier » ne l'avait pas été.** Un Ctrl-C pendant le build,
  la partie longue d'un vrai déploiement, perdait-il aussi le rapport de `deploy.sh` ? Personne ne
  le testait : la suite de `deploy.sh` signale le script seul, sans les copies de sortie de
  `release.sh`. C'est un raccord entre deux fichiers, et la doctrine dit qu'un tel raccord a droit à
  son propre test. Écrit dans `deployment-chain.test.js` : rouge sous 5.3 sans la correction. La
  réponse était oui.
- **Aucune mutation écrite à partir de ce que le code doit refuser.** Dix ont été faites : ignorer
  une partie des signaux seulement, les rétablir à moitié, ignorer après coup, retirer `-p` ou `-a`.
  Une a survécu partout : sans `-a`, une copie écrit à sa propre position dans le fichier, et
  écrase ce que l'autre y a ajouté. Aucun test ne faisait parler stderr avant stdout. Une autre ne
  survit que sous 5.3, où elle est équivalente puisque bash ignore déjà INT de lui-même. Elle
  n'est détectée que sous le bash de la production, que la CI ne fait pas tourner.
- **La passe mécanique n'avait pas été relancée** après l'ajout des tests. Refaite dans `debian:12`
  (bash 5.2.15, celui d'alwaysdata) et dans `ubuntu:26.04` : 0 survivant sur 76 lignes, dans les
  deux.

**Piste d'article** : « fini » est une affirmation, la doctrine est la vérification. Le bilan
demandé à froid a trouvé un défaut latent que personne n'avait vu.

---

## 6. La cascade derrière les failles

Les 25 avis de l'audit avaient presque tous un correctif prêt dans une PR Renovate, bloquée par ce
test. Plus sournois : la maintenance du lockfile, seule à pouvoir corriger les 13 avis npm
transitifs, était marquée « Rate-Limited » — les PR restées ouvertes atteignaient la limite de trois
PR simultanées. Un test rouge bloquait toute la chaîne des mises à jour.

Une fois tout fusionné, il restait deux avis, `glob` et `minimatch`, que rien ne pouvait corriger :
les versions corrigées n'existent que dans de nouvelles majeures, et les quatre paquets qui les
imposent (ESLint, js-beautify et deux autres) sont déjà à leur dernière version. Forcer ces
majeures par des `overrides` aurait échangé une faille sans exposition contre une casse possible de
l'outillage. Elles sont acceptées, avec un motif et une revue à un mois (LUMN-86). Et l'avis `braces`,
accepté depuis octobre, avait tout simplement été retiré par GitHub le 23 octobre.

---

## 7. « Le site n'est toujours pas en ligne »

En fin de session, Laurent a posé la vraie question : des semaines d'effort, un backlog plein de
priorités, et toujours rien en ligne. La réponse tenait dans les liens de LUMN-54. Sur sept tickets
qui bloquaient la mise en production, deux seulement protégeaient un site exposé (le plafond de
`/up`, les en-têtes de sécurité). Les autres automatisaient la façon de livrer : versions
numérotées, approbation, synchronisation JIRA. « En ligne » était devenu « en ligne au moyen d'une
chaîne de livraison parfaite », et la chaîne était encore en chantier.

La décision : **le site part d'abord à la main** (LUMN-96), avec les scripts qui servent déjà la
préproduction, et l'automatisation livrera les versions suivantes (LUMN-54, révisé). Mais pas
avant que le contenu soit complet : un portfolio à moitié rempli ne sert pas mieux qu'un portfolio
absent. Tout le reste est gelé jusqu'à la bascule.

En chemin, trois découvertes que personne n'avait en tête :

- **Le domaine, ses DNS et la messagerie sont chez one.com**, depuis 2014, et le domaine n'a ni
  SPF ni DMARC : le courrier de `contact@` part probablement en spam. Déplacer les DNS en premier
  aurait coupé la redirection vers l'ancien site avant que le nouveau soit prêt. D'où l'ordre :
  la messagerie d'abord, MX seulement (LUMN-95), les serveurs DNS ensuite.
- **Les sauvegardes existaient déjà** : alwaysdata garde trente jours de dumps quotidiens, hors
  site. Ce qui manquait, c'était d'en avoir restauré un une fois.
- **Vingt-neuf tickets attendent en « En préproduction »**, arrivés avant que les versions
  existent. La mise en production automatisée ne fait avancer que les tickets rattachés à une
  version : sans un geste explicite, elle les aurait laissés en plan pour toujours.

**Piste d'article** : un démonstrateur Agile qui ne livre pas ne démontre rien. Livrer tôt, puis
industrialiser.

## 8. Le ticket qui aurait aggravé ce qu'il corrigeait

Premier ticket du chemin vers la mise en ligne : LUMN-92, plafonner `/up` à 60 appels par minute,
parce que la route est publique et interroge la base. Avant d'écrire une ligne, j'ai compté les
requêtes de chaque route avec les pilotes de la production. `/up` en fait **une**, sans session ;
la page d'accueil **cinq**, parce que toute page lit et écrit sa session en base. `/up` était la
route la moins chère du site.

Le plafond prévu, compté dans le cache par défaut — donc en base — aurait fait passer `/up` à **sept
requêtes, dont un verrou de ligne**, à chaque appel, refusé ou non. Et quelqu'un qui veut charger la
base boucle sur une page, que le plafond n'aurait jamais touchée.

Le ticket est devenu une décision : pas de plafond, un test qui maintient `/up` à sa requête
unique, et une documentation qui dit ce qui protège vraiment le site d'un flot de requêtes — l'anti-DDoS
de l'hébergeur, pas Laravel.

**Piste d'article** : mesurer avant de corriger. Le ticket décrivait un risque plausible ; la mesure
a montré qu'il visait la mauvaise route, et que sa solution aurait multiplié par sept le coût de la
seule route sobre.

Puis la même leçon qu'en début de soirée, une seconde fois. J'avais un test (« `/up` fait une
requête ») et son mutant, et je m'apprêtais à conclure. Laurent : « Il n'y a qu'un test et son
témoin négatif ? » Ce test protégeait la *conséquence* de la décision sur la base, pas la décision.
Un plafond qui compte dans un fichier ne coûte aucune requête : il passait le test, et aurait fait
répondre `429` à la supervision. Le second test appelle `/up` cent fois ; le mutant « limiteur en
fichier » ne le passe pas. Et un mutant qui semblait arrêté à 150 par minute ne l'était qu'à cause
des compteurs laissés par le précédent : rejoué sur un cache propre, il passe — limite écrite, pas
cachée.

## Décisions

- **La CI reste sur `ubuntu-latest`**, décidé deux fois le même jour. La première fois sur un
  motif faux, l'absence d'alerte de montée de version : Renovate suit les labels `runs-on` et les
  images `container:`, et j'aurais dû le vérifier au moment où l'argument a été donné. La seconde
  fois en connaissance de cause. J'avais proposé, dans l'ordre, un conteneur `debian:12` en CI et
  une stack Docker calquée sur la production, puis seulement d'épingler les runners. Laurent a
  écarté les trois : de l'outillage contre un événement qui survient tous les deux ou trois ans.
  Les points de contrôle existent sans rien construire : une montée de version chez alwaysdata, le
  retrait d'une image par GitHub, et un test qui rougit, comme aujourd'hui.
- **Piste d'article** : le bon réflexe face à un incident n'est pas toujours d'empêcher qu'il se
  reproduise. Quand il est rare et qu'un test le signale déjà, il suffit de savoir le diagnostiquer
  vite.
- Le serveur alwaysdata tourne sous Debian 12, bash 5.2.15 : pas touché aujourd'hui. Relevé
  directement par SSH — le shell de connexion y est fish, ce que le script disait déjà en tête.
- **Node reste en 24** : alwaysdata ne propose pas encore Node 26, et le build tourne sur le
  serveur. Node 24 est maintenu jusqu'en avril 2028 ; rien ne presse.
- **Mise en ligne à la main avant l'automatisation** (LUMN-96), contenu complet exigé (LUMN-19),
  ancien site retiré, messagerie chez alwaysdata (LUMN-95), sauvegardes d'alwaysdata conservées
  telles quelles avec une restauration vérifiée une fois.
