## Étapes de la session, dans l'ordre

### 1. Petits rattrapages backend

  Anecdote : j'avais mis "tous les jours" sans préciser la durée de rétention, ce qui aurait tout gardé indéfiniment.

### 2. Conventions de code SCSS — Stylelint + Prettier

**Pourquoi avant de toucher à quoi que ce soit d'autre ?**
Parce que sans linter, le SCSS s'entropie silencieusement. Sur un projet comme myFormasup (sans nommer), on se retrouve avec 300 fichiers SCSS incohérents où personne ne sait plus quelle règle s'applique à quoi.

**Ce qu'on a mis en place :**
- `stylelint` + `stylelint-config-standard-scss` + `stylelint-order` (ordre alphabétique des propriétés)
- `prettier` + `stylelint-config-prettier-scss` (pour éviter les conflits entre les deux)
- Config dans `.stylelintrc.json` et `.prettierrc.json`

**Ce qu'on a découvert en lançant le linter pour la première fois :**
122 violations dans le SCSS existant (quelques heures seulement après le premier commit !).
- Valeurs `hue` sans unité `deg` (`142` → `142deg`)
- Alpha en notation décimale au lieu de pourcentage (`0.08` → `8%`)
- Sélecteurs d'attributs sans guillemets (`[data-theme=sprawl]` → `[data-theme='sprawl']`)
- Propriétés CSS non triées alphabétiquement

Toutes corrigées automatiquement avec `--fix`. → **Leçon** : sans linter, ces incohérences s'accumulent sans jamais être visibles jusqu'au jour où quelqu'un doit maintenir le code.

### 3. Husky + lint-staged — Le verrou qualité sur le commit

**Philosophie :** les conventions ne valent rien si elles ne sont pas enforced automatiquement.
Un développeur fatigué à 23h va commit sans relire. Husky ne dort jamais.

**Ce qui tourne dans le pre-commit :**
```
npx lint-staged          → lint + format des fichiers SCSS/JS stagés
npm run test:unit:run    → tous les tests unitaires (rapides, < 1s)
```

**Ce qui N'est PAS dans le pre-commit :**
Les tests E2E Playwright. Ils nécessitent un serveur en cours d'exécution, prennent plusieurs dizaines de secondes,
et leur place est en CI, pas localement. → **Bonne pratique** que j'ai failli rater (l'idée initiale était de tout mettre
dans le pre-commit — l'instinct du "plus c'est safe, mieux c'est" qui se retourne contre toi en pratique).

### 4. Favicons SVG dynamiques et Anti-FOUC

**Le problème :** trois thèmes CSS, trois ambiances visuelles différentes.
Un favicon vert terminal sur un thème steampunk cuivré, ça casse l'immersion.

**La solution :** trois fichiers SVG (un par thème), swappés dynamiquement par JS.

- `favicon-sprawl.svg` : hexagone plat, vert #4dff5c sur fond sombre
- `favicon-steampunk.svg` : engrenage 8 dents (path SVG calculé à la main)
- `favicon-neon-noir.svg` : diamant avec diamant intérieur, cyan #5ec8ea

**Le piège du FOUC (Flash Of Unstyled Content) :**
Le thème est stocké en `localStorage`. Sans précaution, au chargement de la page :
1. Le HTML s'affiche avec le thème par défaut (Sprawl)
2. Le JS charge et applique le bon thème
→ Flash visible d'un thème à l'autre + mauvais favicon pendant 200ms.

**La solution :** un script inline dans le `<head>`, avant tout autre JS, qui lit `localStorage` et applique
`data-theme` **et** le bon `href` de favicon avant le premier rendu. Imperceptible.

### 5. Tests unitaires Vue — Vitest

**Stack :** Vitest + @vue/test-utils + happy-dom (environnement DOM léger, sans Chromium)

**Composant ThemeSwitcher :** 5 tests
- Thème par défaut : Sprawl
- Application du thème : `data-theme`, `localStorage`, favicon
- Bascule entre les 3 thèmes
- Restauration depuis `localStorage` valide
- Ignorer un thème inconnu dans `localStorage`

**Point important sur les `aria-label` :** au cours de cette session, j'ai failli commettre une erreur classique :
traduire en anglais les `aria-label` Vue (ex: `"Changer de thème"`) parce qu'ils "ressemblent à des commentaires de code".
**Non.** Les `aria-label` sont du contenu accessible pour les lecteurs d'écran — ils doivent être dans la langue du site
(ici le français). Les commentaires de code sont en anglais ; le contenu utilisateur est dans la langue de l'utilisateur.

### 6. Tests E2E + accessibilité WCAG 2.1 AA — Playwright + axe-core

**Pourquoi l'accessibilité dès le départ ?**
Parce que corriger l'accessibilité après coup, c'est souvent tout refaire.
Un ratio de contraste insuffisant implique de revoir les couleurs, les tailles, parfois la structure.
Autant le garantir structurellement.

**Ce qu'on a trouvé (et corrigé) :**

*Thème Sprawl — 8 violations WCAG :*
- Le `h2` utilisait `text-secondary` (jaune ambré) sur fond sombre → ratio insuffisant → passage à `text-primary` (vert terminal)
- Titres de sections avec opacity `/50` → ratio insuffisant → suppression de l'opacité
- Labels de catégories `text-secondary/50` → ratio catastrophique → `text-base-content/70`
- Footer : `opacity-50` sur le conteneur parent composait TOUTES les couleurs enfants → déplacé sur le `<p>` uniquement

*Thème Steampunk — 1 violation :*
- Couleur `--color-primary` trop sombre (oklch 66%) → ratio 3.95 contre le fond brun → remontée à oklch 75%

**Découverte importante sur l'opacité CSS :**
`opacity` sur un élément parent s'applique à **tous** ses descendants, y compris les textes, bordures, et backgrounds.
Ce n'est pas la même chose que `color: oklch(... / 70%)`. Piège classique, documenté dans les tests de diagnostic.

### 7. La séquence de boot — BootSequence.vue

**L'idée :** au lieu d'une page qui s'affiche brutalement, une séquence de terminal cyberpunk qui se joue une seule fois
par session de navigateur (`sessionStorage`), skippable par clic ou touche.

**Références littéraires :** univers Neuromancer de William Gibson
- ONO-SENDAI CYBERSPACE 7 (le deck de Case)
- BAMA GRID / CONURB (Boston-Atlanta Metropolitan Axis, le Sprawl)
- Wintermute (l'IA de Tessier-Ashpool, qui refuse la connexion)
- Black ICE TESSIER-ASHPOOL SEC v4.1 (le programme de sécurité)
- Kuang Grade Mark Eleven (le programme de craquage)
- SEFALHIK (mon handle de codeur)

**Détails techniques remarquables :**

*Données système réelles captées au montage :*
Date/heure/fuseau horaire, OS (parsé depuis userAgent), navigateur, nombre de cœurs CPU,
RAM (navigator.deviceMemory), résolution écran, numéro de série aléatoire ONO7-XXXXXXXX.

*Barre de progression ICE en mise à jour in-place :*
Les 6 frames de la progression (`0% → 100%`) occupent la même ligne DOM au lieu d'en ajouter 6.
Mécanisme : `line.group` + `splice()` sur le tableau réactif + `:key="line.group ? line.group : i"` dans le template.
Sans ce mécanisme, Vue crée un nouvel élément DOM à chaque frame.

*Géolocalisation par IP → mapping univers Gibson :*
- `fetch('https://ipapi.co/json/')` au montage (max 3s, timeout gracieux)
- Résultat mis en cache dans `sessionStorage` (clé `geo_data`) pour éviter le rate-limit du tier gratuit (1000 req/jour)
- Mapping : France → `EUROPEAN SPRAWL / PARIS CONURB` ; Japon → `PACIFIC RIM / CHIBA CITY` (ref. directe Neuromancer) ;
  Turquie → `ISTANBUL RELAY / BOSPHORUS NODE` (ref. directe, Istanbul dans Neuromancer) ; US East Coast → `BAMA SPRAWL` ; etc.
- En cas d'échec : fallback `UNCHARTED GRID / ORIGIN MASKED` — aucune erreur visible

*Mention Dantec sur la home page :*
"Neuromatrix online — biocortex active" — référence à Maurice Dantec (Les Racines du Mal, Babylon Babies).
En anglais sur le site malgré les protestations imaginaires de Dantec.

### 8. Extraction utilitaire — utils/boot.js

**Pourquoi extraire les fonctions pures du composant Vue ?**
Un composant Vue n'est pas testable unitairement sur ses fonctions internes.
`<script setup>` encapsule tout ; on ne peut pas `import { getBrowserName } from './BootSequence.vue'`.

**Ce qui a été extrait :**
- `getBrowserName(ua)` — détection navigateur depuis userAgent
- `getOSName(ua)` — détection OS depuis userAgent
- `maskIp(ip)` — masquage IPv4 et IPv6
- `toGibsonLocation(data)` — mapping géo → univers Gibson
- `fetchGeoData()` — fetch ipapi.co avec cache

**Paramètre `ua` avec valeur par défaut :**
```js
function getBrowserName(ua = navigator.userAgent) { ... }
```
En prod : appelé sans argument, utilise `navigator.userAgent`.
En test : on passe directement la chaîne UA → **aucun mock de global nécessaire**.
C'est le principe de l'injection de dépendance appliqué aux fonctions pures.

### 9. Tests des fonctions pures — boot.test.js (36 tests)

**Ce que les tests ont trouvé immédiatement :**

Un vrai bug dans `getOSName` : les conditions `Linux` et `Mac OS X` interceptaient
les user-agents Android et iOS avant que les checks mobiles ne soient évalués.
- Android UA : contient toujours "Linux" → détecté à tort comme `LINUX_X86_64`
- iPhone/iPad UA : contient toujours "Mac OS X" → détecté à tort comme `DARWIN`

**Correction :** inverser l'ordre des conditions (mobile avant desktop).
**Leçon :** sans tests, ce bug serait passé inaperçu en dev (on teste sur desktop),
pour se manifester chez les visiteurs mobiles.

**Tests notables :**
- `toGibsonLocation` : 11 cas (fallback null, fallback error, FR, JP, TR, US East/West/Mid/Unknown, pays inconnu, stripping ASN, troncature carrier)
- `maskIp` : IPv4, IPv6, null, undefined, chaîne vide
- `fetchGeoData` : fetch réussi, erreur réseau, abort

### 10. Tests du composant BootSequence — BootSequence.test.js (8 tests)

**Mocking :** `vi.mock('../../utils/boot', ...)` pour remplacer `fetchGeoData` par une version synchrone.
Sans mock, le test dépendrait d'une API externe → instable en CI.

**`vi.useFakeTimers()` + `flushPromises()` :**
Le `onMounted` est async (il await fetchGeoData). Il faut flusher les microtasks après le mount
pour que le composant finisse son initialisation avant d'asserter.
Les 700ms du fade-out sont avancés avec `vi.advanceTimersByTimeAsync(700)`.

**Test sur le nettoyage (`onUnmounted`) :**
Vérifie qu'après démontage du composant, un keydown ne ré-écrit pas en sessionStorage.
C'est le genre de test qui semble anecdotique mais qui prévient les memory leaks en SPA.

### 11. Tests E2E BootSequence — boot-sequence.spec.js (5 tests)

**Bug Playwright découvert :** `page.keyboard.press('Escape')` échouait silencieusement.
Deux causes combinées :
1. Après `page.goto()`, le focus n'est pas garanti sur le document → le keydown ne remonte pas
2. Timeout 2000ms trop serré : 700ms (timer JS dismiss) + 700ms (transition CSS Vue) = 1400ms minimum,
   sans compter le polling Playwright

**Fix :** `await page.locator('body').focus()` avant le keypress + timeout porté à 3000ms.

## Décisions d'architecture à retenir pour les articles

1. **Islands architecture Vue** : pas d'app Vue globale, chaque composant interactif est monté indépendamment sur son nœud DOM.
   Avantage : le SSR Blade garde la main sur le SEO, Vue n'intervient que là où c'est nécessaire.

2. **Séparation stricte logique/présentation** : `utils/boot.js` contient les fonctions testables indépendamment du composant Vue.
   Règle : si une fonction peut être extraite sans perdre de sens, elle doit l'être.

3. **Tests unitaires en pre-commit, E2E en CI** : distinction fondamentale de performance et de dépendances.

4. **Accessibilité dès le jour 1** : axe-core intégré dans les tests E2E, pas en option.

5. **Convention before feature** : on n'a écrit aucune feature avant d'avoir linter + formatter + hooks en place.
