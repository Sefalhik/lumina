# Session du 3 mai 2026 — Journal de bord
## Base de travail pour la série de blogs « Construire cardascia-it.org »

> **Usage** : brouillon de travail, non exhaustif sur le code mais complet sur les décisions et les pourquoi.
> À reprendre quand le moteur de blog sera en place.

---

## Contexte général

Le site n'est pas encore en production. C'est exactement pour ça qu'on a décidé de faire quelque
chose qu'on ne peut pratiquement jamais se permettre sur un projet actif : mettre à jour **toute la
stack d'un coup**, breaking changes inclus. Zéro filet, mais zéro regret non plus.

Cette session, c'est l'histoire de cette mise à jour — ce qui s'est passé sans accroc, ce qui a
révélé des anomalies cachées, et ce qui a été bloqué par une panne d'infrastructure externe. Spoiler :
le meilleur outil pour gérer les mises à jour importantes, c'est souvent de ne pas avoir
d'utilisateurs.

---

## L'inventaire de départ

Avant de changer quoi que ce soit, on fait un état des lieux. `composer outdated` côté PHP,
`npm outdated` côté JS, et une vérification manuelle de l'infra système (PHP, Node, PostgreSQL,
Redis, FrankenPHP).

Le résultat côté JS est rassurant : tout est en retard de quelques versions patch ou minor, rien de
cassant. Côté PHP, c'est plus intéressant : les dépendances Laravel sont en décalage mineur, mais
PHPUnit est à `12.5.23` alors que la version `13.1.8` est disponible — un saut de version majeure.

L'infra révèle quelque chose d'inattendu.

---

## La découverte : un mismatch PHP silencieux

En vérifiant la version du binaire FrankenPHP embarqué dans le projet, on tombe sur :

```
FrankenPHP vv1.12.2 PHP 8.5.5 Caddy v2.11.2
```

Pendant ce temps, le PHP système — celui qu'utilisent `artisan`, `composer` et PHPUnit — est en
`8.4.20`. Ce n'est pas une erreur de configuration, c'est la façon dont FrankenPHP fonctionne : il
embarque son propre runtime PHP, indépendant de ce qui est installé sur la machine.

La conséquence concrète : le code tourne sur PHP 8.5 en "production" (même locale), mais les tests
s'exécutent sur PHP 8.4. Si une régression ou une incompatibilité apparaissait entre les deux
versions, les tests ne la verraient pas.

La solution est simple : installer `php8.5-cli` pour aligner le CLI sur le runtime FrankenPHP. Le
dépôt `ppa:ondrej/php` (maintenu par Ondřej Surý, membre de l'équipe PHP et mainteneur des packages
Debian/Ubuntu depuis des années) a tout ce qu'il faut. C'est lui qui fournit les versions PHP
récentes pour Ubuntu — son dépôt `packages.sury.org` pour Debian, et le PPA Launchpad pour Ubuntu.

Sauf que ce jour-là, `ppa.launchpadcontent.net` est en panne. Timeout total, plusieurs tentatives,
option `--no-update`, `--fix-missing`, `ForceIPv4` — rien n'y fait. Et `packages.sury.org` n'héberge
que les distributions Debian (bookworm, trixie…), pas Ubuntu Noble. Il n'existe pas de miroir
officiel de remplacement pour Ubuntu.

Ce point est mis de côté. Le mismatch est documenté, la correction est planifiée, mais on ne bloque
pas toute la session sur une panne externe. C'est une des rares fois où "réessayer demain" est la
bonne réponse technique.

## JS : la mise à jour sans drama

`npm update` règle tout en une commande. 56 packages mis à jour, zéro vulnérabilité, zéro breaking
change. Vue passe de `3.5.32` à `3.5.33`, Vite de `8.0.8` à `8.0.10`, Vitest de `4.1.4` à `4.1.5`,
et ainsi de suite.

Rien à dire. C'est exactement ce à quoi on s'attend d'un écosystème JS bien tenu — les versions
patch et minor arrivent souvent et changent peu. Versionner en `^x.y.z` et laisser `npm update`
faire le travail, ça marche.

## PHP : les dépendances non-PHPUnit

`composer update` sans toucher la contrainte PHPUnit pour l'instant. Laravel passe de `13.5` à
`13.7`, Octane de `2.17.1` à `2.17.3`, Spatie Laravel Permission de `7.3.0` à `7.4.1`, et toute la
galaxie Symfony (polyfills, console, routing…) passe en `8.0.9` et `1.37.0`.

Un nouveau package apparaît en transitif : `symfony/polyfill-php86`. Il n'est pas encore utile sur
PHP 8.4 ou 8.5, mais sa présence indique que les mainteneurs préparent déjà la compatibilité PHP 8.6.
C'est un signal de bonne santé de l'écosystème.

Résultat : tout s'installe proprement, `package:discover` valide tous les packages, aucune erreur.

## PHPUnit 12 → 13 : le saut de version majeure

C'est l'étape qui mobilise le plus d'attention. Mettre à jour la contrainte dans `composer.json` de
`^12.5.12` à `^13.0`, puis lancer `composer update phpunit/phpunit --with-all-dependencies`.

Le `--with-all-dependencies` est important : PHPUnit entraîne toute la famille `sebastian/*` dans
sa mise à jour. Sans ce flag, Composer pourrait refuser d'upgrader certains packages transitifs dont
les nouvelles versions sortent elles aussi du semver des contraintes actuelles.

L'installation place PHPUnit en `13.1.8` et met à jour 19 autres packages (`phpunit/php-code-coverage`
passe de `12.5.6` à `14.1.6` — deux versions majeures d'un coup, uniquement parce que le versioning
de ce package suit celui de PHPUnit).

Puis les tests tournent. 12/12 verts, aucun breaking change à corriger. Pour ce projet, c'est
logique : les tests n'utilisent que des APIs stables de PHPUnit (assertions, `setUp`, fakes Laravel).
Les APIs retirées entre PHPUnit 12 et 13 concernent principalement des méthodes dépréciées depuis
PHPUnit 10 — si le code était propre avant, la migration est transparente.

## La vraie anomalie : SQLite dans `phpunit.xml`

En préparant la migration vers PostgreSQL pour les tests, on découvre que `phpunit.xml` avait une
configuration qui aurait dû alerter dès le premier commit :

```xml
<env name="DB_CONNECTION" value="sqlite"/>
<env name="DB_DATABASE" value=":memory:"/>
```

Alors que le `CLAUDE.md` du projet (et la bonne pratique générale) impose PostgreSQL pour les tests.
Ce genre de divergence est classique : on part en SQLite pour aller vite, on oublie de revenir
dessus, et un beau jour on découvre qu'un test qui passait en `:memory:` échoue en production parce
que PostgreSQL gère différemment les contraintes de clé étrangère, la sensibilité à la casse, les
types de colonnes ou le comportement des transactions.

SQLite est un excellent outil. C'est juste le mauvais outil pour tester une application dont la base
de données cible est PostgreSQL.

---

## Isoler les tests de la base de production

La migration vers PostgreSQL pour les tests soulève une question légitime : comment s'assurer que
les tests ne touchent jamais à la base de données réelle ?

La réponse est dans l'architecture même de la configuration. Dans `phpunit.xml`, on remplace les
vars SQLite par :

```xml
<env name="DB_CONNECTION" value="pgsql"/>
<env name="DB_HOST" value="127.0.0.1"/>
<env name="DB_PORT" value="5433"/>
<env name="DB_DATABASE" value="cardascia_it_test"/>
```

Et on crée une base `cardascia_it_test` dédiée sur le serveur PostgreSQL local.

Ce qui n'apparaît pas dans `phpunit.xml` : le username et le mot de passe. Ce n'est pas un oubli.
Quand PHPUnit injecte ses variables d'environnement via `<env>`, celles-ci prennent priorité sur
les valeurs lues dans `.env` par Laravel. Les variables non définies dans `phpunit.xml` sont donc
lues depuis `.env` normalement — credentials inclus. Résultat : les secrets restent dans `.env`
(non commité), et `phpunit.xml` (commité) ne contient que des informations non-sensibles.

La base `cardascia_it` (production) et `cardascia_it_test` (tests) coexistent sur le même serveur
local, avec les mêmes credentials, mais sont deux bases distinctes. Laravel ne peut pas écrire
dans la mauvaise par accident : si `DB_DATABASE=cardascia_it_test` est forcé par PHPUnit, c'est
`cardascia_it_test` qui est touchée, point.

## I18n : de 2 langues à 24 langues officielles de l'UE

La deuxième grande partie de la session concerne l'internationalisation. Le site supportait `fr` et
`en`. L'ambition : les 24 langues officielles de l'Union Européenne.

```
bg cs da de el en es et fi fr ga hr hu it lt lv mt nl pl pt ro sk sl sv
```

### L'architecture en trois couches

Il y a trois espaces distincts qui ont chacun leur outillage :

- **Blade** (`lang/fr/*.php`) — les chaînes rendu côté serveur, accessibles via `__()`
- **Vue islands** (`resources/js/i18n/*.json`) — les chaînes côté client, via `vue-i18n`
- **Contenu CMS** — colonnes JSON PostgreSQL avec `spatie/laravel-translatable` (à venir)

Ces couches sont intentionnellement séparées. Vouloir les fusionner pour simplifier serait une
fausse bonne idée : leurs contraintes sont différentes (SSR vs CSR, latence serveur vs bundle JS).

### Charger 24 fichiers JSON sans les lister à la main

Avec 2 locales, on pouvait écrire `import fr from './i18n/fr.json'`. Avec 24, ça devient absurde.
La solution : `import.meta.glob` de Vite.

```js
const modules = import.meta.glob('../i18n/*.json', { eager: true });
const messages = Object.fromEntries(
    Object.entries(modules).map(([path, mod]) => [
        path.match(/\/(\w+)\.json$/)[1],
        mod.default,
    ]),
);
```

Vite résout les chemins au build et génère le code d'import statique correspondant. Ajouter une
nouvelle locale se résume à créer le fichier JSON — zéro modification dans `i18n.js`.

### Le middleware SetLocale et les routes préfixées

Toutes les routes publiques sont désormais préfixées par `/{lang}/`. Le middleware `SetLocale`
appelle `App::setLocale($lang)` à chaque requête, ce qui positionne la locale Laravel pour `__()`
et pour l'attribut `<html lang>` dans le template Blade.

La liste des codes supportés est dans `config/i18n.php` — un endroit unique, lu par les routes
(contrainte `where`), le middleware, et le LanguageSwitcher.

La route racine `/` redirige intelligemment : elle délègue à `LocaleResolver`, un service qui
itère sur `getLanguages()` (header `Accept-Language` déjà trié par q-factor par Symfony) et retourne
le premier code présent dans la liste des locales supportées. Fallback sur `fr` si rien ne matche.

Un détail qui compte : `getPreferredLanguage($supported)` de Symfony retourne `$locales[0]` comme
fallback quand aucune langue ne matche — jamais `null`. Utiliser `?? $default` aurait été du dead
code. L'itération manuelle sur `getLanguages()` donne un contrôle explicite sur le fallback.

## La commande `php artisan i18n:translate`

Traduire 24 locales à la main est hors de question. La commande appelle l'API Anthropic (Claude
Haiku) avec un prompt structuré et des règles claires : traduire uniquement les valeurs, jamais
les clés, conserver les placeholders `{name}`, ne pas toucher aux noms propres.

### Deux niveaux d'optimisation

La vraie difficulté n'est pas d'appeler l'API — c'est de ne pas l'appeler inutilement. Deux
mécanismes s'emboîtent :

**Niveau 1 — checksum de fichier.** Si `lang/fr/nav.php` n'a pas changé depuis la dernière
exécution (SHA-256 comparé), on ne traite pas du tout ce fichier. C'est une économie totale : zéro
appel API, zéro comparaison de clé.

**Niveau 2 — cache par clé avec TTL.** Quand le fichier a changé, on compare clé par clé avec le
snapshot précédent. Les clés dont la valeur source est inchangée sont cherchées dans un cache JSON
local (TTL de 6 mois). Seules les clés nouvelles ou modifiées depuis moins de 6 mois font l'objet
d'un appel API.

Le cache est stocké dans `storage/app/i18n/` — des fichiers JSON, pas Redis, pas une table. La
raison : Redis est volatile (`cache:clear` le détruit), une table aurait besoin d'une migration, et
les fichiers JSON sont lisibles, diffables, et persistants. Zéro dépendance supplémentaire.

### Pourquoi pas `getPreferredLanguage` pour le cache

Un piège classique : stocker les traductions dans Redis avec `cache()`. Ça semble simple, mais la
première fois qu'on vide le cache applicatif pour résoudre un bug en prod, toutes les traductions
disparaissent et la commande doit tout retranscrire. La douleur est proportionnelle au nombre de
locales et de clés.

## LanguageSwitcher : drapeau + filtre rapide

24 langues dans une liste déroulante, c'est beaucoup à faire défiler. Le composant final :

- **Bouton** : drapeau emoji + code locale (`🇫🇷 fr`)
- **Dropdown** : champ filtre en haut (filtre en temps réel par nom natif ou code), liste
  scrollable de hauteur fixe, drapeau + nom natif pour chaque option

Le filtre est un `computed` Vue sur un `ref` texte — aucune complexité. La vraie décision était
d'extraire `urlFor` (construction d'URL par remplacement du premier segment de chemin) en
fonction pure dans `utils/language-switcher.js`. Sans extraction, `window.location` serait appelé
directement dans la template — non testable unitairement.

## La question du périmètre de couverture de tests

Un incident de session instructif : en ajoutant des tests pour `TranslationCache`, la couverture
est tombée à 52%. La réaction instinctive : exclure `app/Console` du scope de couverture. C'est
une mauvaise réponse — on masque le problème au lieu de le résoudre.

La vraie cause : `composer test:coverage` ne lançait que la suite Unit, mais les tests de la
commande artisan sont des Feature tests. La correction : passer à `--testsuite=Unit,Feature` dans
`check-coverage.php`. Exclure du code pour faire passer un seuil de couverture, c'est l'inverse
de ce à quoi sert le seuil.

---

## try/catch vs vérification de retour pour les I/O fichier en Laravel

Un autre piège subtil : dans `TranslationCache`, les blocs `try/catch (\Throwable $e)` autour des
appels `file_get_contents` et `file_put_contents` semblaient atteignables. Le reflex "ces fonctions
retournent false, elles ne lèvent pas d'exception" est correct en PHP pur — mais pas en Laravel.

Laravel enregistre un gestionnaire d'erreurs (`HandleExceptions`) qui convertit les `E_WARNING` PHP
(dont ceux générés par un `file_get_contents` sur un fichier non-lisible) en `ErrorException`. Dans
le contexte Laravel, les `try/catch` **sont** nécessaires, et ils **sont** atteignables. Les tester
avec `chmod(0000)` le confirme.

## Les tests E2E et la boot overlay

Les tests Playwright du ThemeSwitcher échouaient avec un timeout de 30 secondes — le bouton
"Changer de thème" était introuvable. Cause : la boot overlay (qui couvre toute la page) était
active, bloquant toute interaction.

La solution : `page.addInitScript()` qui pose `sessionStorage.setItem('boot_sequence_played', '1')`
**avant** le premier script de la page. Le composant Vue vérifie ce flag au `onMounted` et ne
monte pas l'overlay. C'est plus propre qu'un clic de dismiss dans chaque `beforeEach`.

Deuxième subtilité : `[role="option"]` sans scope ramasse les options de **tous** les composants
de la page (ThemeSwitcher + LanguageSwitcher = 27 options). Il faut toujours scoper au bon
`[role="listbox"]` : `page.getByRole('listbox', { name: '…' }).getByRole('option')`.

## Ce qu'on retient

**Sur les mises à jour agressives.** Le "on met tout à jour maintenant parce qu'on peut" a une
vraie valeur en début de projet. La dette de version s'accumule vite et devient douloureuse à
rembourser plus tard. PHPUnit 12 → 13 en plein milieu d'un projet actif avec 500 tests, c'est
stressant. En début de projet avec 12 tests, c'est indolore.

**Sur le mismatch PHP CLI / FrankenPHP.** C'est un angle mort classique avec les runtimes embarqués.
Docker a le même problème si on n'est pas vigilant. La leçon : toujours vérifier que la version PHP
utilisée pour les tests correspond à celle qui fait tourner le code. Ici, la solution est en attente
d'une panne Launchpad — mais au moins, elle est documentée et planifiée.

**Sur SQLite vs PostgreSQL pour les tests.** La règle est simple : tester avec la même base de
données qu'en production. Les "ça marche en SQLite" ne signifient pas grand-chose quand le schéma
utilise des types, des contraintes ou des comportements spécifiques à PostgreSQL. Le coût de la
bonne configuration est une commande `CREATE DATABASE` — le coût de la mauvaise est un bug silencieux
qu'on découvre en prod.

**Sur les pannes d'infra externe.** Launchpad peut tomber. Le dépôt npm peut avoir des problèmes.
Le registre Packagist peut être lent. Avoir une stratégie "on note, on avance, on revient" évite
de bloquer une session entière sur quelque chose sur lequel on n'a aucune prise.

**Sur le périmètre de couverture.** Exclure du code pour faire passer un seuil, c'est tricher.
La bonne réponse est toujours de se demander pourquoi le code n'est pas couvert — et d'y répondre
avec des tests, pas avec une exclusion.

**Sur la logique métier dans les routes.** Une closure dans `web.php` qui fait plus qu'orchestrer
est un signal. `LocaleResolver` est minuscule, mais il a un nom, un test, et peut être étendu sans
toucher au fichier de routes. C'est le genre de discipline qui fait la différence sur la durée.
