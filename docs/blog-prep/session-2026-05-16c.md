## Contexte général

Ajout d'ESLint v9 flat config sur un projet Vue 3 + Vite existant. Le projet avait déjà Prettier
(formatage) et Stylelint (SCSS), mais aucune analyse statique JS. L'objectif : combler ce trou
sans créer de friction inutile dans le workflow de commit.

---

## Partie 1 — Choix de la stack

### ESLint v9 et la flat config

ESLint v9 a abandonné le format de config historique (`.eslintrc.*`) au profit du format "flat"
(`eslint.config.js`). C'est un fichier JS standard, pas de JSON avec des clés magiques, pas de
`extends` comme chaîne de strings opaques. On importe des objets et on les compose dans un tableau.

Avantage concret : la config est lisible et traçable. Chaque règle active a une source visible.

### Packages retenus

- **`eslint`** — le core, v10 (installée par npm en résolvant la dernière compatible)
- **`@eslint/js`** — exporte `js.configs.recommended`, le set de règles JS standard
- **`eslint-plugin-vue`** — règles Vue 3, maintenu par l'équipe Vue core
- **`eslint-config-prettier`** — désactive *uniquement* les règles ESLint qui entreraient en
  conflit avec Prettier (mise en forme, espaces, virgules…). Prettier reste le formateur, ESLint
  reste l'analyseur. Les deux coexistent sans se marcher dessus.
- **`globals`** — package qui fournit des listes de globaux pré-construites (`browser`, `node`,
  `es2021`…). Nécessaire en flat config car `env: { browser: true }` n'existe plus.

### Ce qui a été écarté

- **`@typescript-eslint`** — le projet est en JS pur, pas de TypeScript
- **`eslint-plugin-tailwindcss`** — Tailwind v4 utilise du CSS natif (`@layer`, `@utility`),
  pas des `className` arbitraires en HTML. Le plugin n'apporte rien ici.
- **`eslint-plugin-vitest`** — les règles Vitest (no-test-only, etc.) peuvent être ajoutées plus
  tard si le besoin se manifeste. Pas de valeur ajoutée immédiate sur ce projet.

## Partie 2 — La flat config en détail

```js
import js from '@eslint/js';
import pluginVue from 'eslint-plugin-vue';
import prettier from 'eslint-config-prettier';
import globals from 'globals';

export default [
    js.configs.recommended,
    ...pluginVue.configs['flat/recommended'],
    prettier,
    {
        files: ['resources/js/**/*.{js,vue}'],
        languageOptions: {
            globals: {
                ...globals.browser,
                route: 'readonly', // Ziggy — injected via @routes Blade directive
            },
        },
        rules: {
            'vue/component-api-style': ['error', ['script-setup']],
            'no-var': 'error',
            'prefer-const': 'error',
        },
    },
    {
        ignores: ['vendor/**', 'node_modules/**', 'public/**', 'storage/**', 'bootstrap/cache/**'],
    },
];
```

### Pourquoi `flat/recommended` et pas `vue3-recommended` ?

`eslint-plugin-vue` expose deux variantes pour la flat config :
- `configs['flat/recommended']` → le format flat natif, tableau d'objets, compatible ESLint v9
- `configs['vue3-recommended']` → l'ancien format, pour compatibilité ascendante avec `.eslintrc`

En flat config, seule la première variante fonctionne correctement. La seconde nécessite un
wrapper de compatibilité (`@eslint/eslintrc`) qui ajoute de la complexité sans bénéfice.

### Pourquoi `eslint-config-prettier` en dernier ?

La flat config est un tableau traité dans l'ordre. Les règles des entrées suivantes écrasent
celles des entrées précédentes. Mettre `prettier` en troisième position (après les deux plugins)
garantit que ses désactivations s'appliquent à toutes les règles de formatage activées avant.

Si on le mettait avant `pluginVue.configs['flat/recommended']`, des règles Vue de formatage
(indentation de template, etc.) resteraient actives et entreraient en conflit avec Prettier.

### Le global `route`

Ziggy est une bibliothèque Laravel qui génère un helper JS `route()` injecté globalement dans
toutes les pages via la directive Blade `@routes`. Ce n'est pas un import — c'est une variable
globale disponible dans le contexte browser. Sans la déclarer dans `globals`, ESLint remonte
`'route' is not defined` sur chaque usage.

La déclaration `'readonly'` (et non `'writable'`) est intentionnelle : on ne réassigne jamais
`route`, c'est une fonction injectable en lecture seule.

## Partie 3 — Les 108 erreurs de départ (et pourquoi presque toutes étaient du bruit)

Premier run sur le code existant : 108 problèmes, 104 errors. Intimidant. En réalité :

**103 sur 104 erreurs = `no-undef` sur des globaux browser.**

`document`, `window`, `sessionStorage`, `localStorage`, `navigator`, `screen`, `fetch`,
`setTimeout`, `clearTimeout`, `AbortController`, `KeyboardEvent`, `DOMException`… Tous ces noms
sont inconnus d'ESLint par défaut parce que, sans `languageOptions.globals`, ESLint suppose un
environnement Node.js pur. Il ne sait pas que le code tournera dans un navigateur.

La correction : une seule ligne dans la config — `...globals.browser`. Après ça, 103 erreurs
disparaissent d'un coup.

**La vraie erreur dans le code** : `let timers = []` dans `BootSequence.vue`. Le tableau est
initialisé vide et jamais réassigné (seul son contenu change via `push`). `let` était donc
incorrect — `const` est juste, et c'est ce que ESLint demandait avec `prefer-const`.

**Les 4 warnings restants** : `vue/attributes-order` — ordre des attributs Vue dans le template
(`aria-hidden` et `ref` après des event listeners). Auto-fixés par `eslint --fix`. Ce ne sont
pas des bugs, mais des conventions d'ordre que le plugin Vue enforce pour la lisibilité.

**Ce qu'on apprend** : quand ESLint sort 100+ erreurs sur un codebase existant, la première étape
est de catégoriser avant de corriger. Très souvent, la majorité relève d'une configuration
manquante (environnement, globals) plutôt que de vrais bugs. Corriger la config coûte une ligne ;
corriger 103 faux positifs à la main coûterait une heure.

## Partie 4 — Intégration dans le workflow

### Pre-commit : vérification sans auto-fix

Dans `lint-staged`, ESLint est branché en vérification seule (pas de `--fix`) :

```json
{
    "resources/js/**/*.{js,vue}": [
        "prettier --write",
        "eslint"
    ]
}
```

L'ordre est intentionnel : Prettier formate d'abord, puis ESLint vérifie. Si Prettier introduit
quelque chose qu'ESLint désapprouverait (ce qui ne devrait pas arriver avec `eslint-config-prettier`
en place), ESLint bloque le commit.

Le choix du mode vérification-seule au commit est délibéré : l'auto-fix modifie silencieusement
des fichiers au moment du commit, ce qui peut surprendre et cache des problèmes que le dev devrait
comprendre. `lint:js:fix` existe pour le fix manuel, à la demande.

### Scripts npm

```bash
npm run lint:js        # check
npm run lint:js:fix    # fix
```

`lint:js:fix` reste utile pour les migrations (nouveau dev qui rejoint le projet, refactors massifs)
ou quand on veut corriger tous les warnings d'ordre d'attributs d'un coup.

## Sujets d'articles potentiels

1. **"ESLint v9 flat config : de zéro à Vue 3 en 30 lignes"**
   Démystifier la flat config. Comparaison avec l'ancienne syntaxe `.eslintrc`. L'ordre des
   entrées dans le tableau et pourquoi `eslint-config-prettier` doit être en dernier. Le piège
   `flat/recommended` vs `vue3-recommended`. Résultat : une config lisible, sans magie.

2. **"108 erreurs ESLint sur du code propre : anatomie d'un faux positif"**
   Le cas des globaux browser manquants. Comment catégoriser les erreurs avant de corriger.
   `globals.browser` comme ligne de config qui éteint 100 erreurs. Ce que les vrais bugs
   ressemblent quand le bruit est retiré.

3. **"ESLint + Prettier + Stylelint : faire cohabiter trois outils sans conflits"**
   La règle de base : chaque outil a un périmètre exclusif. Prettier = formatage. Stylelint = CSS.
   ESLint = qualité JS/Vue. `eslint-config-prettier` comme interface entre ESLint et Prettier.
   `lint-staged` comme orchestrateur au commit.

4. **"vue/component-api-style : enforcer `<script setup>` par la règle plutôt que par convention"**
   Sur un projet Vue 3 Composition API, `<script setup>` n'est pas optionnel — c'est l'API
   recommandée et la seule autorisée sur ce projet. Mais sans règle ESLint, rien n'empêche un
   dev distrait d'écrire `export default { setup() { ... } }`. La règle `vue/component-api-style`
   rend la convention exécutoire.
