## Partie 1 — Corriger le hook pre-commit : le piège APP_ENV

### Le problème

Dix tests échouaient avec des 419 (CSRF token mismatch) uniquement quand on commitait depuis VSCode.
En lançant `php artisan test --coverage` à la main : tout passait.

La divergence venait du cycle de bootstrap d'artisan. Quand le hook pre-commit invoque
`php artisan test`, artisan lit `.env` en premier — qui contient `APP_ENV=local`. À ce stade,
`VerifyCsrfToken::runningUnitTests()` vérifie `$app['env'] === 'testing'`, et comme
l'environnement est `local`, la vérification CSRF s'applique. Résultat : tous les POST
retournent 419.

Quand on lance manuellement `php artisan test`, la commande `TestCommand` propage `APP_ENV=testing`
au sous-processus PHPUnit avant qu'il ne bootstrappe. Dans le contexte du hook VSCode, cette
propagation ne se produisait pas.

### La solution

Préfixer la commande dans `scripts/check-coverage.php` :

```
APP_ENV=testing php -d pcov.enabled=1 artisan test ...
```

La variable est dans l'environnement du processus *avant* que artisan lise `.env`. Simple,
chirurgical, sans effet de bord.

**Ce qu'on apprend** : `phpunit.xml` peut déclarer `<env name="APP_ENV" value="testing"/>`, mais
sans `force="true"`, cette valeur ne remplace pas une variable déjà présente dans l'environnement du
processus. Le préfixe shell est la solution la plus directe et la plus explicite.

## Partie 2 — Navigation inter-sections et ergonomie admin

### Lien retour vers le site public

L'interface admin n'avait aucun moyen de revenir sur le site public. Ajout d'un bouton
`‹ Voir le site` dans la navbar admin, `target="_blank"`. Le sens inverse (site public → admin)
existait déjà mais sans `target="_blank"` non plus.

Décision : les liens qui traversent les deux sections (admin ↔ public) ouvrent toujours un
nouvel onglet. Rationale : les deux contextes ont des vocations différentes — on ne veut pas
perdre sa page courante en naviguant entre eux.

**Détail `rel="noopener noreferrer"`** : indispensable sur tout `target="_blank"`. Sans lui, la page
ouverte peut accéder à `window.opener` et potentiellement rediriger la page parente. Bonne pratique
de sécurité systématique.

### ThemeSwitcher et LanguageSwitcher absents de l'interface admin

Le layout admin (`layouts/admin.blade.php`) ne chargeait pas `app.js` — uniquement les CSS.
Fix en deux lignes : ajouter `resources/js/app.js` au `@vite` et les deux `<div id="...">` dans
la navbar.

Problème découvert ensuite : le ThemeSwitcher lançait une `TypeError` au changement de thème sur
l'admin car il faisait `document.getElementById('favicon').href = ...` sans guard. L'élément
`#favicon` n'existait pas dans le layout admin.

Deux correctifs distincts :
1. Ajouter `<link rel="icon" id="favicon">` dans le `<head>` de l'admin (avec le script
   anti-FOUC qui synchronise favicon et thème au chargement)
2. Rendre le composant `ThemeSwitcher` robuste : `const favicon = document.getElementById('favicon'); if (favicon) favicon.href = ...`

**Ce qu'on apprend** : un composant Vue réutilisable ne doit jamais supposer qu'un élément DOM
particulier existe dans la page hôte. Le guard `if (el)` est le contrat minimal d'une island.

## Partie 3 — Synchronisation cross-tab du thème et de la langue

### Le problème

Deux onglets ouverts sur le site. On change le thème dans l'un : l'autre ne bouge pas.
Idem pour la langue.

### Pourquoi pas Laravel Echo ?

Laravel Echo sert à diffuser des événements *serveur* vers le client via WebSocket. Ici, il
n'y a pas d'état serveur impliqué — le thème est dans `localStorage`, la locale est dans l'URL.
Echo serait une dépendance lourde (Redis, Reverb ou Pusher, connexion WebSocket permanente) pour
un problème purement client. Overkill total.

### La solution native : l'événement `storage`

Le navigateur émet automatiquement un événement `storage` dans tous les *autres* onglets de la
même origine quand `localStorage` est modifié. C'est exactement la primitive qu'il nous faut.
Zéro dépendance, zéro infra, comportement natif et spécifié.

```js
window.addEventListener('storage', (event) => {
    if (event.key === 'theme' && isValidTheme(event.newValue)) {
        applyTheme(event.newValue);
    }
});
```

### Asymétrie ThemeSwitcher / LanguageSwitcher

Le thème vit dans `localStorage` → la propagation est directe.

La langue vit dans l'URL (le segment `/{lang}/`), pas dans `localStorage`. Le LanguageSwitcher
navigue via des `<a href>`, pas via `localStorage.setItem`. Pour déclencher l'événement `storage`
dans les autres onglets, il faut *écrire* dans localStorage au moment du clic — avant que la
navigation emporte le tab courant :

```js
function onLocaleClick(code) {
    localStorage.setItem('locale', code);
    // navigation se fait normalement via le href de l'<a>
}
```

Dans les autres onglets, l'événement `storage` déclenche une navigation vers l'URL équivalente
calculée par `urlFor()`.

**Ce qu'on apprend** : la propagation cross-tab est une préoccupation légitime dès qu'on a de
l'état client partagé. L'événement `storage` est la solution canonique et sous-utilisée — la plupart
des développeurs ne la connaissent pas et se retournent vers des solutions over-engineered.

## Partie 4 — Extraction de la logique métier vers les utils

### Le problème

En ajoutant la synchronisation cross-tab, on avait glissé de la logique dans les composants Vue
(`applyTheme`, `onStorageChange`, `onLocaleClick`). Ces fonctions étaient maintenant couplées au
cycle de vie Vue et impossibles à tester unitairement sans monter un composant complet.

### La règle d'architecture

Dans ce projet, les composants Vue sont des **orchestrateurs** : ils câblent des primitives Vue
(refs, lifecycle hooks, templates) autour de logique qui vit dans `resources/js/utils/`. La
logique pure va dans les utils, les utils sont couverts par Vitest, les composants sont couverts
par Playwright.

### Ce qu'on a extrait

**`utils/theme.js`** :
- `VALID_THEMES` — source de vérité pour les identifiants valides
- `isValidTheme(id)` — prédicat pur
- `applyTheme(id)` — manipulation DOM sans effet `localStorage`

La séparation `applyTheme` / écriture `localStorage` est intentionnelle : si `applyTheme`
écrivait dans `localStorage`, l'écoute de l'événement `storage` dans le même composant
déclencherait une boucle. La règle est : *write once, react without writing*.

**`utils/language-switcher.js`** :
- `writeLocaleToStorage(code)` ajouté à côté de `urlFor`

### Tests unitaires Vitest

Huit cas pour `theme.js` : exhaustivité de `VALID_THEMES`, comportement de `isValidTheme` sur
les cas limites, `applyTheme` avec/sans `#favicon` dans le DOM, résistance au throw quand
l'élément est absent.

Trois cas pour `writeLocaleToStorage` : écriture, écrasement, isolation des autres clés.

### Tests Playwright cross-tab

Le vrai intérêt : Playwright permet de tester la propagation cross-tab de façon fidèle car les
pages créées dans le même `BrowserContext` partagent le même `localStorage` — exactement comme
de vrais onglets dans le même navigateur.

```js
test('theme change propagates to another open tab', async ({ context }) => {
    await context.addInitScript(() => sessionStorage.setItem('boot_sequence_played', '1'));
    const page1 = await context.newPage();
    const page2 = await context.newPage();
    await page1.goto('/fr/');
    await page2.goto('/fr/');
    // ...
    await expect(page2.locator('html')).toHaveAttribute('data-theme', 'neon-noir');
});
```

`context.addInitScript()` (niveau contexte) applique le script à toutes les pages créées ensuite,
contrairement à `page.addInitScript()` (niveau page). Différence subtile mais importante quand
on crée plusieurs pages dans un test.

## Partie 5 — Epic B : CMS homepage avec spatie/laravel-translatable

### Pourquoi des colonnes JSON pour le multilingue ?

Trois approches classiques :
1. Une table de traductions liée par FK — flexible, complexe à requêter
2. Une colonne par langue — rigide, explose avec 24 locales
3. **Colonne JSON unique** par champ — structure `{"fr": "...", "en": "...", "de": "..."}` dans un seul champ PostgreSQL

`spatie/laravel-translatable` abstrait la troisième approche : `$model->getTranslation('tagline', 'fr')` et `$model->setTranslation('tagline', 'fr', '...')`. PostgreSQL supporte le JSON natif avec indexation et opérateurs `->`. C'est le bon compromis pour un CMS léger.

### setTranslation vs setTranslations — un piège important

`setTranslations('tagline', ['fr' => '...'])` **remplace toutes les locales** par le tableau passé.
`setTranslation('tagline', 'fr', '...')` **met à jour une seule locale** en préservant les autres.

Dans le contrôleur admin, on édite uniquement le français (source de vérité). Les traductions vers les 23 autres langues seront générées par une future commande `cms:translate`. Il est donc impératif d'utiliser `setTranslation` au singulier — sinon chaque sauvegarde admin efface les traductions AI.

### Formulaire admin FR uniquement — décision UX

Trois options envisagées :
1. Formulaire bilingue (FR + langue courante)
2. Formulaire avec preview multilingue intégré
3. **FR uniquement, preview séparé** — formulaire simple, bouton "Voir le site" en nouvel onglet

Option 3 retenue : l'admin édite le FR, la traduction est déléguée à l'API. Toute interface multilangue dans l'admin serait prématurée avant que `cms:translate` existe.

## Partie 6 — Infrastructure de tests E2E : la leçon par l'échec

Cette partie est la plus riche en enseignements concrets sur les pièges de l'outillage E2E.

### Erreur n°1 : tester contre la base de dev

Première approche : les tests Playwright frappaient `https://dev.cardascia-it.org` (base dev). Deux problèmes :
- Les tests de formulaire écrasaient le vrai contenu de la homepage
- Les tests laissaient des utilisateurs résiduels en base

Solution : **base dédiée `cardascia_it_e2e`**, serveur `php artisan serve --port=8001` avec variables d'environnement surchargées (`DB_DATABASE`, `APP_URL`, `SESSION_DOMAIN`, `SESSION_SECURE_COOKIE`). La constante de surcharge est centralisée dans `tests/e2e/helpers/e2e-env.js` et partagée entre `playwright.config.js` (via `webServer.env`) et `global-setup.js`.

`globalSetup` lance `migrate:fresh --force` avant chaque run : ardoise propre garantie.

### Erreur n°2 : `waitForURL` avec le mauvais pattern

Le setup attendait `**/fr/admin/dashboard`. La route réelle est `/{lang}/admin` (un `Route::get('/')` dans un groupe préfixé `admin`). Pattern corrigé en regex : `/\/fr\/admin$/`.

**Ce qu'on apprend** : toujours vérifier l'URL réelle dans le navigateur avant d'écrire un pattern Playwright.

### Erreur n°3 : race condition sur `User::firstOrCreate`

Avec `fullyParallel: true`, plusieurs workers appelaient `/e2e/admin-auth` simultanément. `firstOrCreate` n'est pas atomique : deux processus peuvent tous les deux conclure que l'utilisateur n'existe pas et tenter une insertion concurrente → violation de contrainte unique.

Solution : pattern `storageState` de Playwright. Le projet `setup` s'authentifie une seule fois et sauvegarde les cookies dans `tests/e2e/.auth/admin.json`. Les tests consomment ce fichier via `test.use({ storageState })` sans jamais ré-appeler l'endpoint d'auth.

### Erreur n°4 : cookie de session perdu sur HTTP

Le dev server tourne en HTTPS avec `SESSION_SECURE_COOKIE=true` et `SESSION_DOMAIN=dev.cardascia-it.org`. Le serveur E2E tourne en HTTP sur `localhost:8001`. Le navigateur refuse d'envoyer un cookie `Secure` sur HTTP → session perdue → redirect vers login.

Trois variables à surcharger : `SESSION_SECURE_COOKIE=false`, `SESSION_DOMAIN=localhost`, `APP_URL=http://localhost:8001`.

### Erreur n°5 : session Redis écrite après la réponse

Même avec les bons cookies, le middleware redirigait encore vers la page de setup 2FA. Cause : `SESSION_DRIVER=redis` + FrankenPHP. `StartSession::terminate()` écrit Redis *après* l'envoi de la réponse HTTP. Avec une latence localhost quasi nulle, le browser suit la redirect avant que Redis ne soit écrit → session vide côté serveur.

Fix chirurgical : appel explicite à `request()->session()->save()` dans la route e2e, *avant* le `return redirect()`. Redis est écrit de manière synchrone, avant l'envoi de la réponse.

**Ce qu'on apprend** : en mode worker (Octane/FrankenPHP) ou avec un driver de session externe (Redis), l'hypothèse "la session est sauvegardée quand je renvoie la réponse" est fausse. `terminate()` court-circuite la sauvegarde différée dans les tests à haute vitesse.

### Erreur n°6 : `fill()` respecte `maxlength`

Un test vérifiait la validation côté serveur pour un champ `bio` dépassant 1000 caractères. `page.locator('#bio_fr').fill('x'.repeat(1001))` ne soumettait que 1000 caractères — le navigateur tronque silencieusement à `maxlength`.

Fix : `locator.evaluate((el) => { el.value = 'x'.repeat(1001); })` affecte directement la propriété `value` sans passer par les événements DOM, contournant `maxlength`.

## Partie 7 — Tests d'accessibilité automatisés avec axe-core

### La démarche

Plutôt que de cocher l'accessibilité manuellement, chaque vue est scannée automatiquement via `@axe-core/playwright` sur les 3 thèmes. Le test échoue dès qu'une violation WCAG 2.1 AA est détectée, avec le ratio de contraste précis et l'élément incriminé.

### Ce qu'on a découvert : les opacités destructrices

Les thèmes sombres du site ont des fonds quasi-noirs (`#030409`, `#100502`, `#01030b`). Les classes Tailwind d'opacité réduisent le contraste de façon multiplicative dans l'espace perceptuel.

Constats empiriques après scan :
- `text-base-content/40` sur 10px → 2.6 à 2.9:1 (seuil : 4.5:1) ❌
- `text-base-content/50` sur 12–14px → 3.5 à 4.1:1 ❌
- `text-secondary/50` → aussi bas que 2.04:1 ❌

Seuils sûrs établis par calcul et validés par les tests :
- 10px → `/60` minimum (~4.8:1)
- 12–14px → `/70` minimum (~5:1)
- `secondary` → sans opacité (100%)

**Ce qu'on apprend** : les designs "muted" avec des textes clairs sur fond sombre sont un piège à accessibilité. L'œil humain compense, axe ne ment pas. Tester avec un outil automatisé révèle des violations qu'une review humaine manque systématiquement.

## Partie 8 — Architecture : la règle du service layer

Lors de la review du `HomepageContentController`, Laurent a soulevé un point d'architecture fondamental : même quelques lignes de logique de persistance dans un contrôleur violent le principe de testabilité.

### La règle

> Aucune logique métier dans les contrôleurs, les modèles Eloquent, ni les composants Vue.

Tout ce qui peut être extrait en classe de service (PHP) ou en module util (JS) doit l'être, même si c'est verbeux. Les raisons :

1. **Testabilité unitaire** : un service s'instancie et se teste sans contexte HTTP ni setup Vue
2. **Réutilisabilité** : une future commande `cms:translate` appelant `HomepageContentService::updateTranslation()` est triviale
3. **Séparation des préoccupations** : le contrôleur orchestre, il ne décide pas

L'extraction vers un service a été différée ici faute d'un second appelant — mais notée comme dette technique connue.

**Ce qu'on apprend** : "c'est juste quelques lignes" est exactement l'argument qui mène à des contrôleurs de 300 lignes. La discipline s'applique dès la première ligne de logique non-triviale.
