# Session du 16 mai 2026 (partie D) — Script d'audit local et pipeline CI
## Base de travail pour la série de blogs « Construire cardascia-it.org »

> **Usage** : brouillon de travail, non exhaustif sur le code mais complet sur les décisions et les pourquoi.
> À reprendre quand le moteur de blog sera en place.

---

## Contexte général

Mise en place de l'outillage "dernière ligne de défense" : un script local qui agrège tous les
outils de qualité en une commande, et un pipeline GitHub Actions qui reproduit le sous-ensemble
faisable en environnement de CI.

L'objectif n'est pas de dupliquer le pre-commit hook — il reste la protection au commit. Ces
deux outils couvrent des moments différents.

---

## Partie 1 — Les trois couches de protection qualité

Le projet a maintenant trois couches :

| Moment | Outil | Ce qu'il fait |
|--------|-------|---------------|
| Commit | Husky + lint-staged | Prettier, ESLint, couverture JS + PHP (80%) |
| Avant push | `npm run check:full` | Tout + Playwright E2E |
| PR / push | GitHub Actions CI | PHPStan + PHPUnit + ESLint + Stylelint + Vitest |

**Pourquoi trois couches et pas une ?**

Chaque couche a un coût et un périmètre différents. Le pre-commit hook doit être rapide (< 30s)
pour ne pas décourager les commits fréquents — donc pas d'E2E, pas de PHPStan. Le script local
est complet mais optionnel — il protège le push, pas le commit. La CI tourne dans un
environnement neutre et est la seule couche qui détecte les problèmes de configuration locale
("ça marche chez moi").

## Partie 2 — `scripts/check.sh` : conception du script d'audit

### La décision clef : bash pur, pas un outil dédié

Des outils comme `lefthook`, `husky` avec des étapes supplémentaires, ou `nx` peuvent orchestrer
des tâches. Mais pour un script d'audit "tout en un" sans dépendance supplémentaire, un script
bash est imbattable en simplicité et portabilité.

### La structure

```bash
step "ESLint"          npm run --silent lint:js
step "Stylelint"       npm run --silent lint:scss
step "PHPStan (app)"   bash -c "PHP_INI_SCAN_DIR=... ./vendor/bin/phpstan analyse"
step "PHPStan (tests)" bash -c "PHP_INI_SCAN_DIR=... ./vendor/bin/phpstan analyse -c phpstan-tests.neon"
step "PHPUnit"         bash -c "php artisan config:clear --quiet && php artisan test"
step "Vitest"          npm run --silent test:unit:run
step "Playwright E2E"  npm run --silent test:e2e
```

Chaque `step` :
1. Lance la commande, capture stdout + stderr dans un fichier temporaire
2. Affiche ✔ (vert) ou ✗ FAILED (rouge) avec le temps écoulé
3. En cas d'échec, affiche les 40 premières lignes de sortie avec indentation
4. Incrémente les compteurs PASS/FAIL
5. Accumule le nom de l'étape dans `FAILED_STEPS[]`

Le script continue même si une étape échoue — on voit tous les problèmes d'un coup, pas
seulement le premier. `set -uo pipefail` (sans `set -e`) est intentionnel pour cette raison.

### La sortie finale

```
  All 7 checks passed  in 41s
```

ou, en cas d'échec :

```
  2 / 7 checks failed  in 38s

  ✗  PHPUnit
  ✗  Playwright E2E
```

Simple, actionnable. Le dev sait exactement quoi corriger avant de push.

### `--silent` dans les scripts npm

Les commandes npm émettent par défaut un header (`> nom-script`) et diverses infos sur le package.
`--silent` supprime tout ça. Résultat : la sortie capturée par `step` ne contient que ce que
l'outil lui-même écrit — plus facile à lire quand on l'affiche indentée sous le ✗.

## Partie 3 — GitHub Actions : les décisions d'architecture

### Un seul fichier, deux jobs parallèles

Un seul `ci.yml` plutôt que `php.yml` + `js.yml` séparés. Avantage : un seul statut à vérifier
sur la PR, une seule entrée dans l'historique CI. Inconvénient : moins de flexibilité pour
déclencher sélectivement. Sur un projet solo, la flexibilité ne vaut pas la complexité additionnelle.

Les deux jobs tournent en parallèle — pas de `needs:` entre eux. Raison : ils sont complètement
indépendants. Un bug PHP n'affecte pas les tests JS et vice-versa. La parallélisation réduit le
temps d'attente sur la PR.

### PostgreSQL comme service Docker

```yaml
services:
  postgres:
    image: postgres:16
    env:
      POSTGRES_USER: postgres
      POSTGRES_PASSWORD: postgres
      POSTGRES_DB: cardascia_it_test
    ports:
      - 5432:5432
    options: >-
      --health-cmd pg_isready
      --health-interval 10s
      --health-timeout 5s
      --health-retries 5
```

Le `options` avec `--health-cmd pg_isready` est critique : sans lui, le step suivant peut démarrer
avant que PostgreSQL soit prêt à accepter des connexions. GitHub Actions attend que le health
check passe avant de marquer le service comme "ready".

### Le problème du port 5433 → 5432

`phpunit.xml` contient `<env name="DB_PORT" value="5433"/>` — le port local de PostgreSQL (5433
au lieu du défaut 5432, choix spécifique à ce setup). En CI, le service PostgreSQL est sur le
port 5432 (le défaut Docker).

La solution est simple : définir `DB_PORT: 5432` dans le bloc `env:` du job CI. Les variables
d'environnement du processus prennent priorité sur les `<env>` de `phpunit.xml` — ces derniers
n'écrasent les valeurs existantes que si l'attribut `force="true"` est présent (non utilisé ici).

Pas besoin de modifier `phpunit.xml` ou de maintenir deux configs. Une ligne dans le workflow.

### `PHP_INI_SCAN_DIR` nécessaire en CI aussi

En local, il fallait exporter `PHP_INI_SCAN_DIR=/etc/php/8.5/cli/conf.d` pour que les workers
PHPStan héritent du chemin des extensions. Contrairement à ce qui était supposé au départ, ce
problème se produit aussi en CI.

Les runners GitHub Actions tournent sur Ubuntu et utilisent la même installation APT de PHP que
l'environnement local Debian/Ubuntu — avec le même découpage `php.ini` principal + répertoire
`conf.d`. `shivammathur/setup-php` installe les extensions dans `conf.d/`, pas directement dans
`php.ini`. Le mécanisme de héritage défaillant dans les workers ReactPHP est donc identique.

Solution : définir `PHP_INI_SCAN_DIR: /etc/php/8.5/cli/conf.d` dans le bloc `env:` du job PHP,
ce qui force les workers à hériter du chemin via l'environnement du processus parent.

Le chemin `/etc/php/8.5/cli/conf.d` est correct sur Ubuntu (même distribution que les runners
GitHub) — ce n'est pas un chemin arbitraire propre au poste de développement.

### `ANTHROPIC_API_KEY: test_key`

Les tests qui couvrent `i18n:translate` et `cms:translate` utilisent tous `Http::fake()`. Aucun
appel réel n'est fait. Mais la commande valide que la clé est non vide avant de démarrer.
Mettre `test_key` (une valeur quelconque) satisfait cette validation sans exposer une vraie clé.

### Playwright E2E absent du CI

Les tests E2E nécessitent :
- Un serveur Laravel sur le port 8001 (géré par `webServer` de Playwright, mais nécessite PHP)
- Une base `cardascia_it_e2e` distincte
- Un `migrate:fresh` au démarrage (`globalSetup`)

Tout cela est faisable en CI, mais représente une complexité significative (second service
PostgreSQL, attente de `migrate:fresh`, gestion du `storageState` d'auth…). Le rapport
coût/bénéfice sur un projet solo est défavorable : les E2E sont couverts par `npm run check:full`
en local avant chaque push.

## Sujets d'articles potentiels

1. **"Script d'audit qualité en bash : agréger ESLint, PHPStan et PHPUnit en une commande"**
   Anatomie d'un script `check.sh` qui agrège plusieurs outils hétérogènes. La fonction `step()`
   comme pattern réutilisable. Pourquoi `set -uo pipefail` sans `set -e`. `--silent` dans npm.
   La valeur d'un récap final face à des sorties isolées.

2. **"GitHub Actions pour un projet Laravel : PHPStan + PHPUnit avec PostgreSQL"**
   Configuration d'un service Docker PostgreSQL dans un workflow GitHub Actions. Le piège du
   health check (pourquoi `--health-cmd pg_isready` est obligatoire). Surcharger `phpunit.xml`
   avec des variables d'environnement GitHub Actions. `shivammathur/setup-php` et pourquoi
   `PHP_INI_SCAN_DIR` n'est pas nécessaire en CI contrairement au setup local.

3. **"Trois couches de qualité : pre-commit, audit local, CI — quand utiliser quoi ?"**
   Le pre-commit hook comme protection rapide. Le script d'audit comme protection avant push.
   La CI comme filet de sécurité dans un environnement neutre. Pourquoi ces trois niveaux ne
   sont pas redondants malgré leurs recoupements. Le seul argument valable pour ne pas avoir de CI
   (solo, pas de collaborateurs) et pourquoi il ne tient pas vraiment.
