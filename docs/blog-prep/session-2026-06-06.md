## Audit des allowlists Claude Code — les wildcards qui donnent les clés du royaume

Claude Code maintient une liste blanche de commandes qu'il peut exécuter sans demander confirmation. Cette liste (`settings.local.json`) s'est accumulée au fil des sessions de débogage, et l'audit d'aujourd'hui a révélé plusieurs entrées préoccupantes.

### Les patterns dangereux

Cinq entrées accordaient une exécution de code arbitraire, sans le réaliser :

```json
"Bash(php *)",
"Bash(php8.5 *)",
"Bash(/usr/bin/env php *)",
"Bash(node *)",
"Bash(bash -c ' *)"
```

Ces patterns correspondent à ce que les guidelines d'allowlist Claude Code appellent **interpréteurs avec wildcard** — ils sont explicitement listés comme interdits parce qu'ils équivalent à `allow: everything`. Un acteur malveillant (ou un outil mal configuré) pourrait déclencher `php -r "system('rm -rf /')"` sans aucune confirmation.

### Comment ça arrive

Le mécanisme est subtil. Quand Claude exécute une commande non autorisée, il propose un pattern à ajouter à la liste blanche. Lors d'une session de débogage intense (ici, les problèmes PHPStan/FrankenPHP de sessions précédentes), on valide rapidement sans regarder la portée réelle du wildcard. `php /tmp/debug.php` → proposition `Bash(php *)` → validation rapide → backdoor ouverte.

### Les patterns cassés

Dix-huit autres entrées utilisaient une syntaxe incorrecte avec le caractère `:` comme séparateur :

```json
"Bash(npm run:*)",   // ne matche aucune commande npm run
"Bash(git:*)",       // inutile, git est déjà auto-allowé
"Bash(php artisan:*)" // ne matche pas "php artisan test"
```

Claude Code interprète le pattern comme un préfixe littéral. `npm run:*` ne correspond à aucune commande réelle — la protection n'existait pas, mais l'illusion de sécurité si.

### La règle à retenir

Avant de valider une proposition d'allowlist, se demander : **ce pattern pourrait-il exécuter du code arbitraire ?** Si la réponse est oui, refuser et demander un pattern exact à la place.

| À éviter | À préférer |
|----------|-----------|
| `Bash(php *)` | `Bash(php artisan test *)` |
| `Bash(node *)` | `Bash(node -e "const v=...")` (exact) |
| `Bash(bash -c ' *)` | rien — confirmer manuellement |

## Script de mise à jour automatique FrankenPHP

FrankenPHP embarque son propre runtime PHP — il ne dépend pas de la version PHP installée sur la machine hôte. Un `php --version` système à 8.5.7 ne change rien à la version PHP que FrankenPHP utilise en production. Le binaire `./frankenphp` est une unité autonome qu'il faut mettre à jour séparément de Composer et npm.

### Le script

`scripts/update-frankenphp.sh` — appelé via `npm run update:frankenphp` :

1. Détecte la version courante (`./frankenphp --version`)
2. Récupère la dernière release depuis l'API GitHub (`dunglas/frankenphp`)
3. Détecte la plateforme (`uname -s` / `uname -m`) → construit le nom d'asset (`frankenphp-linux-x86_64`, etc.)
4. Si déjà à jour : sortie propre
5. Sinon : affiche current vs latest, demande confirmation (ou skip avec `--force` pour CI/CD)
6. Télécharge dans un fichier temporaire, remplace atomiquement (`mv`), restaure la capability Linux

L'option `--force` est prévue pour l'intégration GitHub Actions future :
```yaml
- run: npm run update:frankenphp -- --force
```

### Le piège setcap

Sur Linux, les ports inférieurs à 1024 sont des **ports privilégiés** : seul root peut y écouter, par défaut. FrankenPHP a besoin d'écouter sur le port 443 (HTTPS) sans être root.

La solution standard est `setcap` — on accorde une capability POSIX spécifique au binaire :

```bash
sudo setcap cap_net_bind_service=+ep ./frankenphp
```

Le problème : **`setcap` est lié à l'inode du fichier, pas à son chemin.** Quand on remplace le binaire via `mv`, l'ancien fichier (avec sa capability) disparaît et le nouveau n'en a pas. FrankenPHP démarre alors avec :

```
listen tcp :443: bind: permission denied
```

Le script de mise à jour re-applique donc `setcap` après chaque remplacement :

```bash
if sudo setcap cap_net_bind_service=+ep "$BINARY" 2>/dev/null; then
  printf "  cap_net_bind_service restored\n"
else
  printf "  Warning: run: sudo setcap cap_net_bind_service=+ep %s\n" "$BINARY"
fi
```

Si `sudo` n'est pas disponible (CI sans privilèges), le warning informe sans bloquer le script.

## Détail technique : redirect GitHub API

L'API GitHub `repos/dunglas/frankenphp/releases/latest` retourne `301 Moved Permanently` — le dépôt a été transféré à un moment. `curl -s` sans `-L` ne suit pas les redirects → réponse vide → `jq: Cannot iterate over null`.

Fix : `curl -sL` pour suivre les redirections automatiquement. Rappel utile pour tout script qui interroge l'API GitHub.

## Régression Vite 8 + vue-i18n 11 — `init_runtime_dom_esm_bundler is not defined`

### Symptôme

Après une mise à jour de dépendances npm, les îlots Vue ne se montent plus en dev. La console affiche :

```
ReferenceError: init_runtime_dom_esm_bundler is not defined
    <anonymous> https://dev.cardascia-it.org:5173/node_modules/.vite/deps/vue-i18n.js:2858
```

L'erreur est strictement limitée au serveur de développement Vite. Les tests Playwright (CI et local) passent — ils tournent contre un build de production (`npm run build`) compilé par Rollup, qui bundle tout en un seul passage et n'a pas ce problème.

### Pourquoi ça se produit

Vite en mode dev ne bundle pas le code applicatif — il le sert en ESM natif. Mais il **pré-bundle les dépendances** `node_modules` via esbuild pour les mettre en cache (`.vite/deps/`). Chaque dépendance devient un chunk séparé.

Quand esbuild pré-bundle vue-i18n, il renomme les exports internes de Vue avec un préfixe `init_` pour gérer l'ordre d'initialisation des modules : `@vue/runtime-dom` devient `init_runtime_dom_esm_bundler`. Ce nom est une référence au chunk Vue voisin dans `.vite/deps/`.

Le problème : au chargement, le chunk vue-i18n s'exécute et appelle `init_runtime_dom_esm_bundler()` — mais le chunk Vue n'a pas encore fini de s'initialiser. La référence est `undefined`. C'est une race condition dans l'ordre d'initialisation des chunks esbuild, aggravée par Vite 8.

### Ce qui ne fonctionne pas

Deux tentatives infructueuses :

**`optimizeDeps.include: ['vue-i18n']`** — ne change rien. Vue-i18n est déjà pré-bundlé par défaut ; `include` force juste l'inclusion explicite mais ne résout pas l'ordre d'init.

**`resolve.alias: { 'vue-i18n': 'vue-i18n/dist/vue-i18n.esm-bundler.js' }`** — inutile : `vue-i18n.esm-bundler.js` n'est qu'un `export * from '../dist/vue-i18n.mjs'`. L'alias ne change pas le fichier réellement chargé.

### La solution

```js
optimizeDeps: {
    exclude: ['vue-i18n'],
    include: ['@intlify/core-base', '@intlify/shared'],
},
```

**`exclude: ['vue-i18n']`** : Vite ne passe plus vue-i18n par esbuild. Il le sert directement en ESM depuis `node_modules`. Ses imports (`import * as Vue from 'vue'`, etc.) sont réécrits à la volée par le middleware Vite — qui les résout dans le bon ordre, sans jamais générer de référence `init_*` cassée.

**`include: ['@intlify/core-base', '@intlify/shared']`** : sans cette ligne, Vite découvrirait les dépendances transitives de vue-i18n au premier chargement de page et déclencherait un reload. Les pré-bundler explicitement évite ce comportement.

### Le diagnostic qui a débusqué le problème

```bash
head -1 node_modules/vue-i18n/dist/vue-i18n.esm-bundler.js
# → export * from '../dist/vue-i18n.mjs'
```

Un seul grep suffit à invalider une piste entière. Garder ce réflexe avant d'essayer une correction.
